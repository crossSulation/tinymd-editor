# tinymd-editor

A mobile-first markdown editor app built directly on **`@milkdown/kit`** (ProseMirror-based), with a custom hand-built UI — not Crepe's prebuilt one. This document defines the architecture to build against.

## App vs. Editor

This codebase is two things at two different levels of reuse:

- **The Editor** — `src/view/Editor.tsx` (plus its supporting files in `src/view/`). A plain, self-contained React component: markdown in via props, changes out via `onChange`. It knows nothing about docIds, SQLite, routing, document metadata, or "this app" — it could be dropped into a different project's UI as-is.
- **The App** — `src/app/` (`HomePage.tsx`, `EditorPage.tsx`, `NewDocumentModal.tsx`) plus the root `src/App.tsx`. This is what's specific to *this* app: a document list (Home), a one-time creation modal (title/author/tags — see "Persistence" below for why this is the *only* place `DocumentMeta` is set), and a page that loads/saves a specific document and renders the Editor around it. `App.tsx` is a thin router between Home and Editor, using local `useState` (no routing library — no URL-based deep links; reconsider only if that's actually needed).

When adding a feature, ask which side it belongs on: UI/behavior of editing a single document's content → Editor (`src/view/`). Anything about *which* document, navigation, or persistence → App (`src/app/`, `src/control/`).

## Tech Stack

- **React + Vite** — app shell. React mounts the editor via `@milkdown/kit`'s vanilla `Editor.make()...create()` API in a `useEffect`; React does not own editor state.
- **`@milkdown/kit`** (ProseMirror-based) — editing engine, used directly rather than through `@milkdown/crepe`. Crepe is Milkdown's ready-made WYSIWYG wrapper, but its prebuilt UI relies on several `:hover`-revealed affordances (e.g. a code block's language picker/copy button only appear on `:hover` — confirmed in Crepe's own theme CSS) that have no equivalent on touch devices. Since mobile is P0, the UI (toolbar, code-block chrome, floating selection menu) is hand-built here instead — see "View" below for exactly what's reused vs. custom.
- **SQLite WASM** (`@sqlite.org/sqlite-wasm`) — document/metadata persistence running in-browser, via OPFS (Origin Private File System) for durable storage. Runs in a dedicated Worker (`src/control/sqlite.worker.ts`), since OPFS's synchronous file API requires one. No server-side DB. Requires `Cross-Origin-Opener-Policy: same-origin` / `Cross-Origin-Embedder-Policy: require-corp` headers (configured in `vite.config.ts` for dev/preview; a production host needs the same). This is the web backend only — see "Persistence" below for the Tauri/Android backend.
- **Tauri 2.0** (`src-tauri/`) — wraps the same web app as a native Android app, for testing on a physical device. No iOS target (needs a Mac/Xcode, not attempted). `npx tauri android dev`/`build` drive it; the web dev server (`npm run dev`) and web build (`npm run build`) are otherwise unaffected and keep working standalone.
- **`milkdown-chunk-editor`** (vendored at `vendor/milkdown-chunk-editor-0.1.0.tgz`, installed as a `file:` dependency so the install stays reproducible without that external path) — only its pure, DOM-free utilities (`splitIntoChunks`, `joinChunks`, `VirtualLayout`) are used, by `VirtualizedEditorController`, for documents large enough to trigger chunked rendering (see the View section below). Its own `ChunkedEditor`/`mountChunk` are NOT used directly — they build a bare `commonmark+gfm+history+listener`-only Milkdown instance per chunk, dropping every custom plugin this app has (Mermaid/LaTeX preview, floating toolbar, placeholder, click-past-end, code-block exit-on-Enter); this app's own `chunkMount.ts` reuses `createMilkdownEditor.ts`'s shared plugin stack instead, so a chunked document keeps full feature parity with a normal one.

Do not add a separate state-management library (Redux/Zustand/etc.) — the Milkdown editor's own state is the source of truth for document content. Do not add an ORM for SQLite WASM — use parameterized SQL directly against the small schema this app needs. Do not add a routing library for App navigation unless URL-based deep linking is actually requested — plain state is sufficient for two pages. **No `:hover`-only UI anywhere in `src/view/`** — touch has no hover state; use `:active` for press feedback and selection-state polling (`isMarkActive`/`isNodeActive` in `commands.ts`) for toggled/pressed looks instead. Every tappable control should be >=44px (the Apple/WCAG touch-target minimum).

## Layered Architecture

### Model (`src/model/`)
Owns data shape and transformation rules outside of what the Milkdown editor instance manages internally (it still owns the document schema and markdown parsing/serialization itself). Holds:
- `document.ts` — `DocumentMeta`/`CustomProperty` types (title, tags, author, timestamps, custom properties) and `createDocumentMeta()`/`touch()` helpers.
- `blocks.ts` — the markdown ⇄ SQLite-row mapping: `splitMarkdownIntoBlocks()` parses markdown (via `remark-parse` + `remark-gfm`) and re-stringifies each top-level node independently, giving one block string per row to persist; `joinBlocksIntoMarkdown()` is the inverse. `remark-gfm` is required — the editor's schema is GFM-based (tables, task lists, strikethrough), and without it a table parses as an inert paragraph instead of a real table node.
- Any schema-level primitives a custom plugin needs that aren't document-specific enough to live in Control.

### View (`src/view/`)
- `Editor.tsx` — picks one of two bodies based on `initialMarkdown.length` vs. `CHUNK_SIZE_THRESHOLD` (50,000 chars, decided once at mount via `useMemo`, not reactive — same "not reactive after mount" contract as `initialMarkdown` itself): below it, the normal single-instance path (`buildMilkdownEditor` from `createMilkdownEditor.ts`, `.create()`'d directly into `.editor-mount`); at or above it, `VirtualizedEditorBody` instead. Owns the `"text" | "draw"` mode state (`ModeHeader.tsx`'s type) and renders, top to bottom: `ModeHeader`, the content area (either body + `DrawLayer`), then the fixed bottom `Toolbar` — only in text mode (`mode === "text" && editor && commands`), where `editor`/`commands` come from whichever path is active (the single instance, or the virtualized path's currently-focused chunk, via `onActiveChange`). Switching to draw mode blurs the ProseMirror view (`editor.ctx.get(editorViewCtx).dom.blur()`) the same way group panels and code-block exit already do.
- `createMilkdownEditor.ts` — `buildMilkdownEditor(opts)`: the one plugin stack (`commonmark`/`gfm`/`listener`/`history`/`clipboard`/`cursor`/`codeBlockComponent`/placeholder/floating-toolbar/click-past-end/code-block-exit-keymap) every Milkdown instance in this app is built from, factored out of `Editor.tsx` so `chunkMount.ts` (below) builds each chunk's instance identically rather than drifting out of sync with the single-editor path.
- `VirtualizedEditorBody.tsx` / `virtualizedEditorController.ts` / `chunkMount.ts` — the chunked/virtualized rendering path for documents over `CHUNK_SIZE_THRESHOLD`, rendered by `Editor.tsx` in place of its normal single instance. `VirtualizedEditorController` is ported from the vendored `milkdown-chunk-editor` package's own `ChunkedEditor` class (split + virtual-layout + per-chunk-instance lifecycle, reusing that package's pure `splitIntoChunks`/`joinChunks`/`VirtualLayout` utilities directly) but mounts each chunk via this app's own `chunkMount.ts` (`mountEditorChunk`, built on `createMilkdownEditor.ts`'s full plugin stack) instead of the package's bare `mountChunk`, and additionally tracks which chunk currently has focus (`activeChunkId`, via each chunk's own `focusin`/`focusout`) so `Toolbar.tsx` has a single editor/commands pair to bind to — the package itself has no such concept, since it wasn't built around one shared toolbar. Chunks are split by heading (`splitIntoChunks`'s own regex-based splitter, levels 1–2 by default) purely for virtualized *rendering*; this is layered entirely on top of the existing Model/Control persistence (`splitMarkdownIntoBlocks`/the `blocks` table are untouched and know nothing about chunks) — `VirtualizedEditorController.onChange` always reports the full rejoined markdown string, so `EditorPage.tsx` is unaffected either way. **Scroll-triggered chunk swaps recycle instances instead of destroying and recreating them** (`sync()`'s recycle step, pairing up outgoing/incoming chunks up to `Math.min(leaving.length, needed.length)`): a real-device measurement showed destroy+recreate (full `Editor.make()...create()`, rebuilding CodeMirror/Mermaid/KaTeX/floating-toolbar from scratch) was the dominant cost of every scroll-triggered swap, not markdown parsing itself. Recycling calls `inst.rebind(chunk)` (`chunkMount.ts`), which flushes the outgoing chunk's content, then calls Milkdown's own `replaceAll(markdown, true)` (from `@milkdown/kit/utils`) to swap the document via a fresh `EditorState` on the **same, already-live** `EditorView` — same DOM node, same already-initialized plugin stack, undo history naturally reset (no cross-chunk undo exists regardless). Only the leftover imbalance (pool growing on first load, or shrinking) falls back to real create/destroy, still parallelized via one combined `Promise.all` (destroy's own teardown work was measured to not yield control promptly enough for "void"-calling it in a loop to actually overlap with other work). **`measure()` corrects a chunk's recorded height in both directions, not just shrinkage** — `estimateHeight()`'s char-count heuristic (`split.ts`) routinely *under*-estimates real content (headings/code/tables/wrapped long lines all render taller than the heuristic assumes), and refusing to correct upward left the next chunk's slot positioned partway through the previous chunk's actual rendered content: a real, confirmed unreachable/un-editable gap, not a cosmetic one. `containIntrinsicSize` on a `.chunk-slot` is only ever `content-visibility: auto`'s placeholder for the "not currently relevant" state — it's `VirtualLayout`'s own height bookkeeping (corrected here) that actually determines sibling positions. **Only the document's actual last chunk gets the single-editor path's 60vh tappable-space-below-content treatment** (`.editor-mount-virtualized .milkdown-chunk-root[data-is-last-chunk="true"] .ProseMirror`, vs. `min-height: 0` for every other chunk) — every other chunk's `.ProseMirror` box ends exactly at its content (by design, so short chunks don't force artificial per-chunk dead zones), which means a tap in the blank space below a short chunk never reaches that chunk's own `view.dom` at all, so `clickPastEnd.ts`'s per-chunk plugin (every chunk gets the full plugin stack, `createClickPastEndPlugin` included) never fires there — confirmed directly as a real, reachable bug for the document's true last chunk specifically. `isLastChunk(chunk)` (comparing `chunk.index` against `store.chunks.length - 1`) is computed at every mount *and* every `rebind()` call and written to `data-is-last-chunk`, since which live instance represents the last chunk changes as chunks get recycled. **The "active chunk" (which chunk's editor/commands `Toolbar.tsx` binds to) is sticky across blur, not cleared by it** — `handleChunkBlur` is a deliberate no-op; clearing is only ever done at the point a chunk's instance stops representing that chunk at all (unmount/recycle, in `sync()`). Blur-clearing used to null `Editor.tsx`'s `editor`/`commands` state the instant any chunk's `view.dom.blur()` fired — including `Toolbar.tsx`'s own `openGroup()`, which blurs the view on purpose to dismiss the keyboard while opening a group panel (same as the single-editor path). Since `<Toolbar>`'s render guard is `editor && commands && <Toolbar .../>`, that null unmounted the Toolbar component mid-click, wiping out the `activeGroupKey` state it was in the middle of setting — confirmed directly as why tapping "+" right after focusing a chunk never opened the Insert panel, even though the tap itself correctly focused the editor. **A chunk's height is also re-measured live while you edit it, not just at mount/rebind time** — `chunkMount.ts`'s `onContentResize` callback fires on every `markdownUpdated` (the controller's `handleChunkResize` coalesces it to one `requestAnimationFrame` per chunk, re-running `measure()`); without this, editing an already-mounted, non-scrolled-past chunk (typing more text, adding/removing a code block) changed its real rendered height while `VirtualLayout`'s recorded height for it stayed frozen at whatever `sync()` last measured, leaving the next chunk's slot positioned mid-content or with a real, un-tappable dead gap before it — confirmed directly as a real bug (not just at scroll-boundaries, but during ordinary editing of any visible chunk). **`sync()` is not guarded against running concurrently with itself** — nothing stops a new scroll-triggered call from starting while a previous one is still `await`ing an in-flight `mountEditorChunk()` (natural with fast/bouncy scrolling, and far more likely on real mobile hardware where mounting takes seconds, not milliseconds) — so `needed`'s "does this chunk already have a live instance" check is against `this.slots`, not `this.mounted`: `this.slots.set(box.id, slot)` happens synchronously, before mounting's `await`, while `this.mounted.set(box.id, inst)` only happens after it resolves; filtering on `this.mounted` left a window where a second, overlapping `sync()` call would see "chunk-0 isn't mounted yet" and create a duplicate slot for it — confirmed directly (reproduced reliably by injecting an artificial delay into `mountEditorChunk` to widen the race window, matching the real-device timing) as the cause of duplicate chunk slots appearing when scrolling back onto an already-mounting chunk. **Page navigation** ("‹ Page N / Total ›" bar, shown only once `totalPages > 1`) is a thin layer on top of this same continuous-scroll virtualization, not a separate rendering mode -- "page N" just means "chunk index N". **The bar itself is rendered by `Editor.tsx`, not `VirtualizedEditorBody`** -- `VirtualizedEditorBody` only reports `{index, total}` up via an `onPageChange` prop (and `null` on unmount), while `Editor.tsx` owns the actual `<div className="virtualized-page-nav">` JSX, positioned as a sibling of `.editor-content` in the same "top header area" row `ModeHeader` occupies, with Prev/Next calling `virtualizedControllerRef.current?.scrollToPage(...)` directly (the same controller ref `Editor.tsx` already holds for `getChunkEditor`). **It didn't start this way, and moved for a confirmed reason**: the bar originally rendered inside `VirtualizedEditorBody`, as a normal flex-row sibling of the scroller within `.virtualized-editor-body` -- correct positioning in document flow, but `DrawLayer`'s canvas (`.draw-layer`, `position: absolute; inset: 0` against `.editor-content`) covers that ENTIRE box regardless of flow, so while draw mode was active the canvas visually (and, since `pointer-events: auto` while active, functionally) covered the nav bar too -- confirmed directly via `elementsFromPoint` at the nav buttons' own coordinates showing the canvas as the topmost element. Moving the bar's rendering to a sibling of `.editor-content` entirely removes it from that overlay's reach structurally (the same reason `ModeHeader`/`Toolbar` were never covered), rather than needing a DrawLayer-specific carve-out (e.g. excluding the nav bar's screen region from the canvas's own hit-testing, which would still leave it visually painted over). `onPageChange` (fired from `sync()`, independent of the mount/unmount bookkeeping) finds the last chunk whose own top has been reached at or before the current `scrollTop` (with a `+2` tolerance: `scrollTargetFor`'s own `EPS` means `scrollToChunk`/`scrollToPage` always land ~1px short of a chunk's exact top, plus up to ~1px more since `scrollTop` is reported as a rounded integer while a chunk's `top` can be sub-pixel -- confirmed directly, a bare `+1` still left the indicator stuck one page behind after every Prev/Next for some chunk heights), with one exception: once scrolled to within 2px of the absolute bottom, it reports the document's true last chunk outright, since a short final chunk's own top can sit past the max reachable `scrollTop` entirely. `scrollToPage(index)` is a one-line wrapper over the already-existing `scrollToChunk()`; `VirtualLayout`, the chunk split, and the recycling machinery are all completely unchanged by this feature. **`overscan` (passed to `VirtualizedEditorController`, defaulting to 1 inside the controller but set explicitly to 2 by `VirtualizedEditorBody.tsx`) controls how many extra chunks beyond the visible range stay mounted** — raised from the unset default after confirming where the real per-chunk cost actually lives: `VirtualLayout`'s own computation (`getRange`'s binary search, `updateHeight`'s prefix-sum rebuild — both O(chunk count), not O(document size)) is sub-millisecond regardless of overscan and was ruled out as a target for offloading to a Worker for that reason; the real cost is `Editor.make()...create()`/`rebind()`'s node-view reconstruction (ProseMirror/CodeMirror/Mermaid/KaTeX), which needs DOM and can't run off the main thread anyway. A wider overscan buffer gives that per-chunk work more lead time to finish before the viewport reaches it during ordinary (non-teleporting) scroll — verified structurally (mounted-chunk-count and recycle-count both scale correctly with the larger buffer, full regression suite unaffected) and now backed by a real on-device number: headless Chrome itself could not surface any measurable cost here (even an artificially injected 150ms per-recycle delay produced zero "stale content visible" misses in either overscan=1 or overscan=2, for the same reason the earlier ~14.5s stutter never reproduced outside a real device), but temporary `console.log` instrumentation in `sync()` (forwarded to `adb logcat` via Tauri's own WebView console bridge, since attaching remote devtools to this build crashes it on attach — see below) on a real Android tablet during manual scrolling showed a single `rebind()`-based recycle taking **607ms** (vs. 0.2-1ms for a pure reposition-only `sync()` with no recycle needed) — confirming the per-chunk cost this whole recycling/overscan design exists to amortize is real and substantial on-device, not just a theoretical concern. `overscan=2` kept 6 chunks mounted throughout that session (vs. ~4 at the unset default of 1), which is the actual margin that cost buys against. A direct overscan=1 vs. overscan=2 on-device comparison was not run (not requested) — the 607ms single-recycle number stands on its own as the dominant-cost confirmation. **Separately discovered and worth flagging**: attaching a remote CDP devtools client to this app's WebView on this specific physical device (a Samsung Galaxy Tab A9+) reliably crashes it (`SIGTRAP`/`TRAP_BRKPT`, same fault address both times) — reproduced once via an invalid Puppeteer `Target.getBrowserContexts` call and once via a clean `chrome-remote-interface` session using only `Runtime`/`Page`/`DOM` domains with no bad calls sent, meaning the crash trigger is attaching a devtools client at all, not any specific command. This is a device/WebView-level issue, unrelated to this app's own code; on-device debugging/profiling work going forward should use the `console.log`-to-`logcat` approach instead of remote devtools on this hardware. **While there's more than one page, every chunk (not just the last) gets a `min-height` equal to the scroller's own available height** (`--chunk-viewport-height`, a CSS custom property the controller keeps in sync with `scroller.clientHeight`), so each page-turn fills the screen like a real page rather than scrolling a fraction of it. Gated behind `data-has-multiple-pages` on the scroller (set once from `store.chunks.length > 1` -- the chunk count never changes after construction, so this never needs to toggle); with exactly one chunk, the existing `data-is-last-chunk` 60vh rule still applies unchanged (same specificity, but the multi-page rule is declared later in `editor-base.css` so it wins via source order whenever both could match). **Changing `--chunk-viewport-height` changes every mounted chunk's real height simultaneously** (keyboard open/close, window resize) -- `handleResize()` (the `ResizeObserver` callback) updates the var and then explicitly re-measures every currently-mounted chunk before calling `sync()`, since nothing else re-triggers `measure()` for an already-mounted, untouched chunk; skipping this would reintroduce the same class of permanently-stale-position bug fixed above, just triggered by resize instead of a missed release. **A visible gap between pages** (`padding-bottom: 1.5rem` + a 1px `border-bottom`, also gated on `data-has-multiple-pages` and likewise excluding the true last chunk — nothing follows it) is applied to `.milkdown-chunk-root` itself, not `.ProseMirror`: padding never collapses (unlike margin, an unreliable way to grow an absolutely-positioned slot's own auto-sized box), so it reliably becomes part of the root's real rendered height, which is exactly what `measure()`'s `getBoundingClientRect()` reads — `VirtualLayout` picks up the gap automatically as part of each page's real height, with no changes needed in `virtualizedEditorController.ts`/`chunkMount.ts`. The gap is deliberately *not* tappable — it sits outside `.ProseMirror`'s own box on purpose, the same way a physical page's edge isn't part of its writable area, so a tap landing there doesn't focus the editor (by design, not a dead-zone regression of the kind described above).
- **A chunk's `root.style.minHeight` placeholder (`chunkMount.ts`) must be released, not left in place, once real content exists** — it's seeded from `estimateHeight()` (the same crude char-count heuristic as above), and since that heuristic counts every blank source line (markdown's normal paragraph separator) as a full line-height, which the renderer collapses, it routinely *over*-estimates real content. Left in place, this created a dead zone *within* `.milkdown-chunk-root` itself, between its real (shorter) `.ProseMirror` content and the wrapper's own bottom edge — outside `.ProseMirror`'s own DOM box, so `clickPastEnd.ts`'s handler (bound to `view.dom`) never even received a tap landing there. `releaseMinHeight()` resets it to `0` one frame after content settles (`await editor.create()` for a fresh mount, after `replaceAll` for a rebind) and, critically, **returns a promise the caller awaits before measuring** — `measure()`'s own `getBoundingClientRect()` read and this release used to be two independently-`requestAnimationFrame`-scheduled operations with no ordering guarantee between them; measuring before release locked `VirtualLayout`'s recorded height at the inflated estimate *permanently* for any chunk that's never touched again (confirmed directly, not a transient race — it never self-corrected, even after 1.5s).
- **`measure()`'s own `getBoundingClientRect()` read can itself return a stale `containIntrinsicSize` placeholder**, independent of the `minHeight` issue above: `content-visibility: auto`'s "is this relevant" determination is an opaque, browser-internal heuristic not synchronized with any single `requestAnimationFrame` or forced-reflow read, and while a slot is still considered "skipped," its reported height reflects `containIntrinsicSize` (the same stale estimate) rather than real layout. Confirmed directly as 100% reproducible on initial mount. Fixed by temporarily forcing `content-visibility: visible` immediately around the `getBoundingClientRect()` call inside `measure()`, then restoring `auto` — forces a real layout read regardless of the skip-state heuristic's own timing.
- **A doc-JSON cache + a dirty-change plugin (ported from a 2026-10-27 `milkdown-chunk-editor` update's own `doc-cache.ts`/`mount-chunk.ts`) cut out the two remaining full-document-parse costs the recycle path above didn't already eliminate.** `VirtualizedEditorController` owns one `DocCache` (imported directly from the vendored package — pure, DOM-free, same precedent as `VirtualLayout`/`splitIntoChunks`/`joinChunks`) for its whole lifetime, keyed by chunk id with each entry guarded by an FNV-1a content fingerprint (`DocCache.get()` only returns a hit if the chunk's current markdown still matches what was cached). Two different costs, two different fixes: **(1) mounting/rebinding a chunk whose markdown is unchanged since it was last parsed** — `chunkMount.ts` checks the cache before both the initial `buildMilkdownEditor()` call (passing the cached JSON through `createMilkdownEditor.ts`'s new `initialDocJson` option, which routes to Milkdown's `{type:'json'}` `defaultValueCtx` variant instead of a markdown string) and `rebind()` (where a hit skips `replaceAll(markdown, true)` entirely in favor of `PMNode.fromJSON(schema, json)` + a manual `tr.replace(0, doc.content.size, new Slice(...))`, ~40x faster per the package's own benchmark). A miss (new/edited content, or a schema-incompatible cache entry — shouldn't happen here since every chunk shares the exact same plugin stack, but guarded anyway) falls back to the original markdown-parse path rather than silently reusing stale content, since a silent fallback failure here would mean one chunk's text rendering under a different chunk's id — real data corruption, not a cosmetic bug. The manual `tr.replace` path also has to reset selection to the doc's first inline position afterward (position 0 isn't inline content and throws; a bare position-mapped carry-over of the old selection isn't guaranteed valid in the new doc either) — ported directly from the package's own `replaceContent()`. **(2) serializing a chunk's content back to markdown when nothing was actually edited** — `flush()` (called on every debounce tick, and before every destroy/rebind) used to unconditionally re-stringify and only *then* check whether the result had changed; it now gates on a `dirty` boolean set by `dirtyPlugin.ts`, a direct ProseMirror plugin watching `tr.docChanged` (not Milkdown's own `listener` plugin, which has its own internal 200ms debounce and a `prevDoc.eq(doc)` check that delays the "did this actually change" signal past the point `chunkMount.ts` needs to gate on it precisely) — transactions tagged `CONTENT_REPLACE_META` (the cache-driven swap above) or `addToHistory:false` are excluded so a recycle/rebind never itself counts as an edit. `VirtualizedEditorController.handleChunkChange` deletes the affected chunk's cache entry on a real edit too — not strictly required for correctness (`DocCache.get()`'s fingerprint check already self-corrects on the next lookup), but avoids holding a known-stale JSON blob in memory. Verified end-to-end via CDP against a 12-section virtualized doc: two full scroll round-trips produced cache hits on every chunk's second-or-later visit (0 content corruption — no chunk ever rendered another chunk's text) and all 13 pure-scroll-triggered `flush()` calls skipped the stringify entirely (0 actually ran); editing a previously-cached chunk then revisiting it correctly produced a cache miss (fingerprint invalidation) with the edit intact, not a revert to stale cached content. The pre-existing 16-script virtualized-editor regression suite was re-run unchanged against this and still passes, with one unrelated pre-existing failure found and bisected during this verification (see Scope Boundaries).
- `ModeHeader.tsx` — the top-of-editor icon toolbar: text/draw mode switcher, plus (only while `mode === "draw"`) pen-style swatches (`PenStyle`/`PEN_STYLES` — Pen/Marker/Highlighter presets of color+width+opacity, also defined here). Icon-only, not tab-styled — no underline, no visible text labels, `aria-label` carries the name, same visual language as the bottom `Toolbar`'s own buttons. Not actually `position: fixed`; it's simply the first child in the flex column, outside the scrollable content area, which already keeps it in place (same reason `Toolbar` doesn't scroll away). **The Draw button is disabled during either path's own brief startup window** (`drawDisabled` prop, `Editor.tsx` passes `isVirtualized ? !anyChunkMounted : !editor`) — found as a real, user-visible gap on a real (slower) device, not a theoretical one: a stroke drawn before Milkdown's `.create()` resolves (single-instance) or before any chunk has mounted at all (virtualized) falls back to DrawLayer's scroll-only anchoring (see its own entry above), which looks *visually identical* on screen to a normal, persisted stroke — nothing about the drawing itself gives any indication it silently won't be saved. Disabling the button for that window prevents the ambiguous state outright instead of needing to explain it after the fact. `anyChunkMounted` is the virtualized-path analogue of the single-instance path's `!editor` check: a plain `useState(false)` flipped to `true` the first time `VirtualizedEditorBody`'s `onChunkReady` fires for any chunk (see `inkPersistence.ts`'s entry above for why `onChunkReady`'s own firing point/timing is itself load-bearing) — once ANY chunk is mounted, `findChunkEditorAtPoint` has something to resolve against for whichever chunk a stroke actually lands on, even if other chunks are still mounting.
- `commands.ts` — `createCommands(schema)`: the toolbar's command set (`toggleBold`/`toggleItalic`/`toggleInlineCode`/`toggleStrikethrough`/`toggleUnderline`/`setTextColor`/`clearTextColor`/`setHeading`/`toggleBlockquote`/`toggleBulletList`/`toggleOrderedList`/`setCodeBlock`/`insertHorizontalRule`/`insertTable`/`insertImage`/`insertVideo`/`insertAudio`/`toggleLink`/`undo`/`redo`), built from `@milkdown/kit/prose/commands` + `@milkdown/kit/prose/schema-list` (the same `prosemirror-commands`/`prosemirror-schema-list` packages, just re-exported through Milkdown) plus `isMarkActive`/`isNodeActive` for active-state highlighting. **Milkdown's own mark names differ from a plain ProseMirror/remark schema**: `emphasis` and `inlineCode`, not `em`/`code` — verified directly against `@milkdown/preset-commonmark`'s source, not assumed. `insertTable` uses `createTable` from `@milkdown/kit/preset/gfm` (the same table-creation helper Crepe itself uses internally) rather than hand-building table nodes. `insertImage` opens the platform's native file picker (`<input type="file" accept="image/*">`), reads the chosen file via `FileReader.readAsDataURL`, and constructs Milkdown's real `image` schema node directly with that base64 `data:` URL as `src` (alt text is derived from the filename, no prompt) — there's no file storage/hosting layer in this app, so the image bytes live inline in the markdown itself rather than at a path/URL; `dispatch` is called asynchronously from the file input's `change`/`FileReader` callbacks, which Milkdown/ProseMirror commands allow (dispatch has no synchronicity requirement). - `DrawLayer.tsx` — a free-floating ink/annotation canvas overlaying the editor's visible content area (PDF-markup style). A controlled component: `active`/`penStyle` come from `Editor.tsx`'s state (set via `ModeHeader`). Owns its own "Clear" button, a drawing action rather than a mode/style switch. Redraws the *entire* current stroke as one `stroke()` call per pointermove rather than stroking each tiny segment separately — needed for the semi-transparent Highlighter preset: per-segment stroking double-blends alpha at overlapping round joints, visibly rendering as a bumpy "string of pearls" instead of a smooth translucent bar (confirmed directly before this fix; re-confirmed, pixel-sampled, after the offscreen-canvas rework below). **Two-canvas (visible + offscreen "committed") compositing, not `getImageData`/`putImageData`**: an in-progress stroke's own baseline used to be restored on every `pointermove` via a `getImageData` snapshot (taken once, on `pointerdown`) + `putImageData` (restored before each re-stroke) — a full CPU-side canvas pixel-buffer copy, twice, at touch-move event rates, confirmed as the actual dominant cost of that path (not the `stroke()` call itself, which Canvas 2D already dispatches to native/hardware-accelerated code regardless). Replaced with a second, never-attached-to-the-DOM `<canvas>` (`committedCanvasRef`/`getCommittedCanvas()`) holding every COMPLETED stroke, kept in sync by `redrawAll` (same function, now rendering onto the committed canvas before blitting it to the visible one); an in-progress stroke's own move handler calls `blitCommittedToVisible()` (a `drawImage` GPU-backed blit) instead of `putImageData`, then strokes the in-progress path on top — same visual result and same "whole path as one `stroke()` call" correctness property, far cheaper per move. **The blit needs an identity-transform reset, not a naive `drawImage(committed, 0, 0)`**: both canvases share the same backing resolution AND the same `ctx.scale(dpr, dpr)` transform (kept in lockstep by the resize effect, which now resizes both canvases together), so a plain `drawImage` through that transform would draw the source's already-device-pixel-sized bitmap scaled up by `dpr` a second time; `blitCommittedToVisible` wraps the draw in `ctx.save()` / `ctx.setTransform(1,0,0,1,0,0)` / `ctx.restore()` to blit 1:1 in raw device-pixel space, then hands back the dpr-scaled transform for whatever CSS-pixel-space stroking the caller does next. **A just-finished stroke must be folded into the committed canvas before the next one starts**: `stopDrawing()` calls `redrawAll()` after pushing the finished stroke into `strokesRef`, and `clear()` calls it too (after emptying `strokesRef`) instead of a direct `clearRect` on just the visible canvas — skipping either would leave the committed canvas's own baseline stale, so the very next stroke's first `blitCommittedToVisible()` call would restore a baseline missing (or still showing) ink that should already be gone/added, visibly flickering it away or resurrecting it the instant a new stroke starts. Verified end-to-end via CDP: the full existing ink-persistence/scroll-anchor/reflow-anchor/chunk-isolation regression suite (9 scripts, spanning both the single-instance and virtualized paths) passes unchanged against this rework, plus a new alpha-sampling check confirming a self-overlapping highlighter stroke still composites as one uniform translucent color with no double-blended spikes at its own crossing points. **WASM was considered and rejected for this same workload** (ink capture/rendering in general, not just this specific optimization): Canvas 2D already dispatches to native, hardware-accelerated code in the browser engine regardless of whether the caller is JS or WASM, and WASM has no direct Canvas/DOM binding of its own — it would still have to call back into JS to touch `CanvasRenderingContext2D`, adding a JS↔WASM boundary crossing (plus typed-array marshaling for anything pixel-sized) without bypassing anything in the actual rendering pipeline. The real bottleneck here (`getImageData`/`putImageData`'s CPU-side pixel-buffer copies) is a memory-bandwidth problem, not a compute problem WASM's raw execution speed would address — the offscreen-canvas/`drawImage` fix above addresses it directly, within the existing pure-JS/Canvas-2D architecture. **Three anchoring strategies, chosen PER POINT at the moment it's drawn (not necessarily uniform across one stroke, though in practice it always is — which anchoring is available doesn't change mid-gesture):**
  - **PM-anchored** (`editor` prop non-null — the single-instance, non-virtualized path only): each point is captured as `{pos, dx, dy}` — `pos` via `view.posAtCoords({left, top})` (falling back to `doc.content.size`, i.e. anchoring to the document's end, for a point in the click-past-end space below the last line), `dx`/`dy` the pixel offset from that position's own on-screen coords (`view.coordsAtPos(pos)`) at capture time, since a position's coords are a thin caret-like rect, not literally where the pen touched. **Real content-position anchoring, not just scroll**: `Editor.tsx` wires a new `onTransaction` option (`createMilkdownEditor.ts`) into the single instance's own `buildMilkdownEditor()` call, implemented as a `dispatchTransaction` override on `editorViewOptionsCtx` — deliberately NOT a `Plugin`'s own `state.apply()` hook (the mechanism `dirtyPlugin.ts` uses for the chunked editor's dirty-tracking) because that runs *before* `view.updateState()`, so `view.coordsAtPos()` called from inside it would read stale, pre-edit layout; the override instead does `view.updateState(view.state.apply(tr))` itself and only *then* calls `onTransaction(tr)`, guaranteeing the DOM already reflects the edit. Verified directly against `@milkdown/core`'s own source that it sets no `dispatchTransaction` of its own (keeps `editorStateCtx` synced via a separate internal Plugin instead, which still runs fine since the override performs the same `state.apply()` call), so this doesn't clobber anything. `DrawLayer`'s own subscriber (registered via `registerTransactionHandler`, a prop Editor.tsx backs with a ref rather than state since transactions can fire many times between renders and must be forwarded synchronously/losslessly) remaps every PM point's `pos` through `tr.mapping.mapResult()` on every doc-changing transaction — a point whose anchor content was deleted is dropped (its stroke along with it, once empty) rather than left pointing at the wrong place — then unconditionally calls `redrawAll()`, not just when a `pos` numerically changed: an edit can change *downstream* layout (e.g. a same-length replacement that wraps differently) without changing any later position's raw integer at all, and `coordsAtPos` naturally picks that up regardless. Verified end-to-end via CDP: drawing over a paragraph, then inserting several paragraphs above it, moved the ink by exactly the paragraph's own measured pixel shift; drawing over a paragraph and then deleting that paragraph's text made the stroke disappear rather than jump to a wrong position. Also verified the `dispatchTransaction` override itself doesn't interfere with undo/redo, the `listener` plugin's own `markdownUpdated`/`selectionUpdated` callbacks, or toolbar command dispatch/active-state highlighting (typing, Ctrl+Z, and Bold-toggle all still behave correctly, plus the existing table-commands/text-color CDP tests — both exercise heavier transaction/command paths — still pass unchanged).
  - **PM-chunk-anchored** (`getChunkEditor` prop present — the virtualized path): the same `{pos, dx, dy}` mechanism as PM-anchored, but there is no single shared `editor`/position space to capture against — each virtualized chunk is its own independent Milkdown `EditorView` with its own position numbering, and "whichever chunk currently has focus" is a transient value that doesn't help for a point landing anywhere else on screen. So each point is resolved against WHICHEVER chunk is actually under it, found via the DOM: `findChunkEditorAtPoint` calls `document.elementsFromPoint(clientX, clientY)` (**plural** — the full element stack at that point, topmost first, not `elementFromPoint`, which would just return this canvas itself, since the canvas sits above the chunk content with `pointer-events: auto` while active) and walks it looking for the nearest ancestor with `chunkMount.ts`'s existing `data-chunk-id` attribute, then resolves that id to a live editor via the `getChunkEditor(chunkId)` prop (backed by `VirtualizedEditorController.getChunkEditor`, a thin `this.mounted.get(chunkId)?.editor ?? null` lookup — `null` for a chunk that isn't currently mounted, the same graceful-skip behavior `editor` going `null` already has for the single-instance path, just scoped per point instead of per component). The actual `posAtCoords`/`coordsAtPos` dance (`captureFromView`) is identical to the single-instance case; only which view it runs against differs. Remapping is the per-chunk analogue of the single-instance transaction subscriber: `registerChunkTransactionHandler`/`registerChunkReadyHandler` props (backed by `chunkMount.ts`'s own `onTransaction` and `VirtualizedEditorController.sync()`'s `onChunkReady`, both threaded through `VirtualizedEditorBody.tsx`) let `DrawLayer` remap/prune only the points tagged with a given chunk id through THAT chunk's own transactions (`PmChunkPoint.chunkId` scopes every mapping/filter operation) and rehydrate/redraw whenever a chunk instance becomes newly readable — covering both a fresh mount AND a later recycle/rebind, since a recycled instance holds entirely different content (and therefore different ink) each time; `handleChunkReady` always treats the document as the source of truth, dropping any existing in-memory points for that chunk id and replacing them with whatever's freshly read, rather than trying to reconcile — simpler, and correct whether this is the chunk's first-ever mount this session or a recycle bringing it back.
  - **Scroll-anchored** (neither of the above available): the original, simplest mechanism — a point is `{clientX, yDoc: clientY + scrollTopAtCaptureTime}`, re-projected on redraw as `clientY: yDoc - currentScrollTop`. Tracks scrolling but not reflow, and never persists (see `inkPersistence.ts` below). This is what either path falls back to only during its own brief startup window — the single instance before its one `editor` has finished mounting, or a virtualized document before any chunk has mounted at all (`findChunkEditorAtPoint` has nothing to find yet) — not a permanent fallback for the virtualized path the way it once was: see `ModeHeader.tsx`'s entry below for the gate that prevents a stroke from silently landing here during that exact window.
  
  Either anchoring mode still needs a scroll-triggered redraw: `view.coordsAtPos()` returns viewport-relative coordinates (like `getBoundingClientRect()`), so it genuinely reports a different position after a pure scroll with no doc change at all, same as the scroll-math path. A capture-phase `scroll` listener on the always-present `.editor-content` wrapper calls `redrawAll()` on every scroll, working for either editor path without `DrawLayer` needing to know which is live: `scroll` events don't bubble, but capture-phase listeners on an ancestor still fire on the way down to the real target regardless, so one listener catches scroll from both the single-instance path's real scroll container (Milkdown's own inner `.milkdown` div, not present in the DOM until `editor.create()` resolves) and the virtualized path's (`.editor-mount-virtualized`) — `getScrollTop()` resolves whichever one is live fresh via `closest(".editor-content")?.querySelector(".milkdown, .editor-mount-virtualized")` rather than caching it. The canvas resize effect (triggered by e.g. `--keyboard-inset` changing) calls `redrawAll()` afterward too, instead of leaving the canvas blank — resizing a `<canvas>` resets its own pixel buffer as a side effect of reassigning `width`/`height`, which the vector-data model recovers from either way. **A real bug found and fixed while adding PM-anchoring**: the scroll/resize effects above intentionally attach their listeners once (`[]` deps, so they don't re-attach on every `editor`/`getChunkEditor` identity change) — but their closures therefore captured whatever value existed the FIRST time those effects ran, which is `null`/`undefined` (nothing has mounted yet at that point), permanently freezing every later `capturePoint`/`resolveClientPoint` call onto that stale value and silently treating every PM-anchored point as unresolvable forever after. Confirmed directly (the scroll-anchor regression test failed after PM-anchoring was added, until this was fixed) — not a theoretical race. Fixed with `editorRef`/`getChunkEditorRef` (refs mirroring those props, assigned directly in the render body so they're current before any effect in the same commit runs), read instead of the props themselves inside `capturePoint`/`resolveClientPoint`/`findChunkEditorAtPoint`.
  
  Every completed stroke is kept as vector data (`Stroke { points: StrokePoint[], penStyle }` in `strokesRef`) rather than only existing as baked canvas pixels, regardless of which anchoring mode its points use — the same underlying reason either mode needs it: a plain raster can't be "re-flowed" or "re-scrolled" on its own, only vector data redrawn fresh each time can. **Both PM-anchored and PM-chunk-anchored strokes persist across reloads** (`inkPersistence.ts`) — a chunk's own `ink` node lives in that chunk's own markdown, exactly like the single instance's lives in the whole document's; scroll-anchored ones still don't — a raw scrollTop has no stable meaning across sessions/devices, so there's nothing worth saving for whatever's drawn during either path's brief startup window. `syncInkSingle()`/`syncInkForChunk(chunkId)` are the two write-back entry points (the chunked one filtering `strokesRef` down to only that chunk's own `pm-chunk` points before writing, and a no-op if that chunk isn't currently mounted — both stroke completion and transaction-triggered pruning only ever happen in response to something that chunk's own live view just did, so this is never actually hit for an unmounted chunk); `stopDrawing()`/`clear()` both branch between calling the single-instance sync or iterating every DISTINCT chunk id touched (defensively, in case a stroke ever spans a chunk boundary, even though in practice one doesn't) and syncing each. `pointer-events: none` on the overlay except the canvas itself (only while active) and its controls, so it never blocks normal text editing while in text mode.
- `inkPersistence.ts` — the custom `ink` node + remark plugin backing DrawLayer's persistence, same `$nodeSchema`/`$remark` pattern as `textColor.ts`/`mediaEmbed.ts`. **Format**: a bare `<ink data="BASE64_JSON">` alone on a line, no closing tag, placed at the very end of the document's markdown — for the virtualized path, that's the very end of each CHUNK's own markdown, independently, since `writeInkData`/`readInkData` operate on whatever `EditorView`/doc they're handed and have no concept of "the whole document" at all. The missing closing tag is deliberate, not an oversight: CommonMark's HTML-block "type 7" rule (an unrecognized tag's complete open tag, alone on a line, surrounded by blank lines) is what makes this parse as ONE opaque `html` mdast node with no sibling-splitting — adding a same-line closing tag (`<ink data="...">...</ink>`) would fail type 7's "nothing else on this line" condition and fall back to ordinary inline-HTML tokenization instead, the harder case `mediaEmbed.ts` had to solve for video/audio by merging split sibling nodes back together. `data` is `base64(encodeURIComponent(JSON.stringify({v:1, strokes:[{penStyle:{color,width,opacity}, points:[{pos,dx,dy}]}]})))` — only `PmPoint`/`PmChunkPoint`-shaped points are ever included; DrawLayer.tsx filters scroll-anchored points out before calling `writeInkData`, and (for the chunked case) filters to one specific chunk id's own points as well. **The `ink` node lives in the real, live ProseMirror document**, not a side channel — `group: "block"`, `atom: true`, `selectable: false`. `toDOM` renders `<div style="position:absolute;width:0;height:0;overflow:hidden" data-ink>` — **deliberately NOT `display:none`**, which is what it originally used (zero visual footprint either way, confirmed directly not to interfere with click-past-end: typing after a tap below the last line correctly inserts before the hidden node, keeping it structurally last). See the **fifth bug**, documented below the other four, for why `display:none` specifically had to go. Written at `doc.content.size` (the true end, of whichever document/chunk is live) so it never perturbs any node's STORED markdown position across a save/reload round trip — re-parsing byte-identical markdown deterministically reproduces the same document tree and position numbering, confirmed directly via a real save/reload round trip rather than just assumed. **A real parsing bug found and fixed**: `@milkdown/preset-commonmark` ships its own remark plugin (registered automatically by `.use(commonmark)`) that normalizes *every* top-level `html` mdast node into a paragraph wrapping a single `html` child, regardless of registration order relative to any other remark plugin — confirmed directly against that plugin's source (`node.children = [cloneLeaf(node)]; node.type = "paragraph"`). This is the exact same implicit-paragraph shape `mediaEmbed.ts`'s video/audio tags already had to unwrap, but for a completely different reason (there it's CommonMark's own inline-content wrapping; here it's Milkdown's own commonmark preset normalizing even a block-level HTML node) — `convertInkNodes` has to check for this paragraph-wrapped shape specifically (not just a bare top-level `html` node) or `readInkData` always finds a plain paragraph instead of the ink node, which is exactly what happened before this was found: ink never survived a reload at all until fixed, confirmed via a real save → reload round trip, not assumed from reading the code. **A second real bug, found after the above was already fixed and persistence appeared to work end-to-end**: `writeInkData`'s own transaction (inserting/updating/removing the `ink` node, always at `doc.content.size`) was NOT excluded from `DrawLayer.tsx`'s own transaction-remapping subscriber, which processes every `tr.docChanged` transaction uniformly. A stroke anchored via `capturePoint`'s click-past-end fallback has `pos === doc.content.size` AT THE TIME IT WAS DRAWN — the exact same position `writeInkData` always inserts the `ink` node at. ProseMirror's default position-mapping bias (`assoc = 1`, "stay after inserted content") pushes a position sitting exactly at an insertion point to AFTER the newly-inserted content, so every write of the ink node bumped that stroke's own anchor to sit after (effectively inside/past) the very metadata node carrying its data — corrupting the position and triggering a cascading second write with the now-wrong value. Confirmed directly (not theoretical) by instrumenting the write/remap chain and observing two `syncInk` calls per stroke instead of one, with the second using a shifted `pos`. Fixed by tagging `writeInkData`'s transaction with a dedicated `INK_SYNC_META` meta flag (exported from this file, same pattern as milkdown-chunk-editor's own `CONTENT_REPLACE_META`) and having `DrawLayer.tsx`'s transaction handler skip it entirely — correct, not a workaround: persisting ink data never changes any real content a stroke could legitimately need to remap against. The chunked transaction handler (`handleChunkTransaction`) excludes BOTH `INK_SYNC_META` and `CONTENT_REPLACE_META` (`dirtyPlugin.ts`'s flag for a recycle/rebind's own content-swap transaction) for the same underlying reason — a recycle swapping a chunk instance to represent an entirely different chunk is meaningless to remap old points through, and unnecessary regardless, since those points simply stop resolving once the chunk-id-to-instance mapping changes (handled separately by `handleChunkReady` re-reading fresh data for whichever chunk that instance represents now). **A third real bug, independent of the others and found only after they were already fixed**: even with correct, uncorrupted positions, a stroke anchored in the click-past-end space failed to redraw after every reload. Root cause: `view.coordsAtPos(pos)` with the *default* `side` parameter (`1`, "measure this position from what comes after it") silently returns a degenerate ALL-ZERO rect — not an exception, a normal-looking but wrong result — for a position at the very end of a text run with nothing meaningfully rendered after it and no focus/caret forcing a layout measurement there; this reproduced consistently regardless of how long the code waited afterward (confirmed directly: waiting one or even two `requestAnimationFrame`s made no difference, ruling out a layout-timing race). Fixed by passing `side: -1` ("measure from what comes before it") to every `coordsAtPos` call in `DrawLayer.tsx` (`captureFromView` and `resolveClientPoint`, shared by both the single-instance and chunked paths), which reliably resolves to the actual rendered text position whether or not the view is focused. **A fourth bug, specific to the virtualized path and found once chunk-aware persistence was actually built**: `VirtualizedEditorController.sync()`'s CREATE path (a chunk mounting for the first time) called `mountEditorChunk()`'s own `onChunkReady` callback from INSIDE `chunkMount.ts`, before `sync()` itself added the new instance to `this.mounted` — so `getChunkEditor(chunkId)` (which reads `this.mounted` directly) still returned `null` at the exact moment `DrawLayer`'s rehydration handler tried to resolve/redraw the chunk's restored points, silently failing to paint them until some unrelated later event forced a redraw. Fixed by removing the `onChunkReady` call from inside `chunkMount.ts`'s initial-mount path entirely and calling it explicitly from `virtualizedEditorController.ts`'s `sync()`, immediately after `this.mounted.set(box.id, inst)` — the RECYCLE path needed no equivalent fix, since its own `this.mounted.set()` already runs before `inst.rebind()` is called at all; `rebind()` itself still fires `onChunkReady` at its own end, correctly, for that path. Confirmed via a direct CDP test asserting ink is visible IMMEDIATELY after reopening a virtualized document, with no scroll or other event needed to "unstick" it. **All four bugs were confirmed via the same style of end-to-end repro** (draw a stroke, navigate back to the document list, immediately reopen the same document) and needed to be found and fixed one at a time — each one masked the next until the previous was already resolved.

**A fifth bug, found much later via a completely different repro, and far more serious than any of the first four**: a USER-REPORTED symptom described as "ink strokes visually stretch when editing the document (e.g. adding lines in the middle)." Root cause, confirmed directly via a long elimination chain (not assumed): the `ink` node's `toDOM` originally rendered `<div style="display:none">`. `display:none` removes an element from the layout tree ENTIRELY — and ProseMirror's own DOM↔position mapping (`view.posAtCoords`, and more importantly the internal logic the view uses to translate a native click into a new `Selection`) depends on every node actually participating in layout. With the ink node rendered this way, **any click anywhere in the document, not just near the ink node itself**, silently failed to move the editor's selection to the clicked position — the selection stayed wherever it was before (confirmed directly: `view.state.selection` was unchanged across the click). Since every USER EDIT after that point (typing, pressing Enter to split a line) therefore happened at whatever STALE position the selection was already at — not where the user actually tapped — the real, underlying cause of "ink stretches when I edit" was that the edit itself was landing somewhere completely unexpected relative to the stroke's own anchored points, not a flaw in the position-remapping math (`tr.mapping`) itself, which was independently re-verified correct throughout. **Isolated via a long elimination chain, each step a separate confirmed experiment**: ruled out canvas-resize/orientation-change code entirely (editing doesn't resize `.draw-layer`'s container, so this is a different code path from the resize-driven bug documented in the Tauri/Android section); ruled out timing (deferring `writeInkData`'s dispatch to a macrotask via `setTimeout` made no difference); ruled out "any transaction dispatch" (dispatching a no-op transaction with identical metadata through the same view did NOT break clicking); ruled out "any document-changing insert" (inserting an ORDINARY paragraph with plain text at the same position did NOT break clicking); ruled out `selectable: false` specifically (flipping it to `true` alone did NOT fix it); confirmed `display:none` specifically by replacing it with `position:absolute;width:0;height:0;overflow:hidden` (same zero visual footprint, still a real box in the layout tree) — clicking was immediately restored. Fixed in `toDOM` as shown above. Verified end-to-end: a direct CDP repro (draw an underline-style stroke across a sentence, split that exact sentence into two paragraphs via Enter at the click point) now correctly splits exactly where clicked, instead of silently landing among trailing empty paragraphs at the document's end; click-past-end, zero visual footprint, and reload-persistence were all re-confirmed unaffected by the `toDOM` change. **One remaining, separate, and entirely expected behavior, confirmed NOT a bug**: if the user's edit genuinely inserts a line break WITHIN the span of text a stroke's own anchor points cover (as opposed to landing at the wrong position due to the bug above), the stroke DOES visibly "reshape" — e.g. an underline across one line correctly splits across both resulting lines once the sentence it tracks is split into two. This is the reflow-anchoring design working as intended (each point independently tracks its own anchored text, wherever that text now renders) — not something this fix changes, and not something there's a design for "preventing" (that would require treating a whole stroke as one rigid, non-reflowing unit, the opposite of what reflow-anchoring is for).
  
  **`handleChunkChange` is a public entry point on `VirtualizedEditorController`, not merely an internal callback** — `Editor.tsx`'s `handleChunkInkPersisted(chunkId)` (wired as `DrawLayer`'s `onChunkInkPersisted` prop) calls it directly after an ink-only write to re-serialize that chunk and push the result through the normal dirty-tracking/flush → `onChange` chain, for the identical reason the single-instance path needs its own `onInkPersisted` bypass (see below): `writeInkData`'s transaction is dispatched with `addToHistory: false`, which `dirtyPlugin.ts`'s own dirty-tracking (like `@milkdown/plugin-listener`'s `markdownUpdated`) never sees, so a draw-only edit to a chunk would otherwise never mark that chunk dirty or reach `EditorPage.tsx`'s debounced save on its own.

  **Write-back and the `addToHistory: false` / listener-plugin interaction**: `writeInkData` (called from DrawLayer's `syncInk()` after every completed stroke, every Clear, and after any transaction that actually moved or pruned a PM-anchored point — the last one deferred via `queueMicrotask` since it fires from inside the `dispatchTransaction` override that's still completing the *original* transaction, see Editor.tsx's `onTransaction` wiring) dispatches with `tr.setMeta("addToHistory", false)`, since persisting a drawing isn't a text edit and shouldn't show up on the undo stack as one. **This has a real, non-obvious consequence, confirmed directly against `@milkdown/plugin-listener`'s own source**: that plugin's `apply()` explicitly skips any transaction where `addToHistory === false`, meaning this transaction never reaches the `listener` plugin's `markdownUpdated` callback at all — Editor.tsx's existing autosave chain (`onMarkdownUpdated` → `onChange` → `EditorPage.tsx`'s debounced SQLite save) does **not** fire for an ink-only change on its own. Confirmed as a real bug this way (draw-only, no text edit, reload → drawing gone), not just reasoned about. Fixed with a dedicated `onInkPersisted` prop: `writeInkData` returns whether it actually dispatched a transaction, `syncInk()` calls `onInkPersisted()` only then, and Editor.tsx's handler re-serializes the current document and calls the app's own `onChange` directly — bypassing the listener plugin for this one case, reusing the exact same downstream save pipeline a text edit would. Verified end-to-end via CDP: save→reload with an edited stroke, save→reload with a draw-only (no text touched) stroke, reflow-after-reload (a rehydrated stroke behaves like a live PM-anchored point, not a frozen snapshot — it moves correctly when content is inserted above it post-reload), click-past-end on a document with a persisted `ink` node at its end, and Clear→reload (the node is actually removed from storage, not just cleared client-side) — all pass.
- `code-block-layout.css` — base chrome, language picker, and the side-by-side code/preview layout for the code-block component. `@milkdown/components` ships **zero CSS of its own** for any component — all of this had to be written from scratch (previously Crepe's theme CSS covered it). Every touch target here is >=44px.
- `toolbar.css` / `editor-base.css` / `draw-layer.css` / `mode-header.css` — bottom toolbar (including its media-selection bar and preview lightbox), base editor chrome (placeholder styling, table borders, image/video thumbnail sizing, keyboard-aware sizing), the draw-layer overlay, and the mode switcher — all written from scratch; there is no Crepe-equivalent theme layer to fall back on. **Images are capped to a 200px thumbnail** (`.editor-mount img`, `max-width`/`max-height: 200px`, aspect ratio preserved via `height: auto`) — the image node's own `toDOM` sets no size at all, so without this an inserted photo rendered at its raw pixel dimensions (a phone-camera photo could be thousands of pixels wide); capped to a thumbnail specifically (not the content width) so it reads as "tap to see full size" (the Toolbar.tsx Preview action above) rather than looking like the image's real size.

**Dependency note:** `vue` is a required runtime dependency here, not an artifact of Crepe — `@milkdown/components` (which `component/code-block` comes from) implements every node view with Vue's `h()` directly (verified in its `package.json` and source). Dropping Crepe does not remove this.

A real Milkdown plugin (`$prose`/`$node` from `@milkdown/utils`, `.use()`'d on the `Editor` before `.create()`) is the right tool whenever you need to hook into the document/schema/decorations directly — `placeholder.ts` is an example.

### Control (`src/control/`)
Owns behavior layered on top of the editor, and all persistence.
- `db.ts` — the public persistence API (`getStorageInfo`, `listDocs`, `createDoc`, `loadDoc`, `saveDoc`, `deleteDoc`): a thin dispatcher that picks `webDb` or `tauriDb` via `isTauri()` (`@tauri-apps/api/core`) at module load. This is the only module View/App code is allowed to call into for persistence — neither side needs to know which backend is active.
- `sqlite.worker.ts` + `webDb.ts` — the web backend. `sqlite.worker.ts` is the actual SQLite WASM database (schema, SQL, transactions), running in a Worker since OPFS's synchronous file API requires one; `webDb.ts` is the main-thread bridge to it (request/response correlation: `{id, type, ...}` in, `{id, ok, result|error}` out).
- `tauriDb.ts` — the Tauri/Android backend, via `@tauri-apps/plugin-sql` (native SQLite over Rust/sqlx, through Tauri's IPC bridge directly from the main thread — no Worker needed, there's no OPFS-style sync-access-handle constraint here). Same two-table schema as `sqlite.worker.ts`, same `DocumentMeta` JSON mapping, but `$1`/`$2`/... placeholders (the plugin's SQLite parameter syntax, not `?`). **No `BEGIN`/`COMMIT` transactions** — confirmed directly against the installed `tauri-plugin-sql` Rust source that every `db.execute()`/`db.select()` call does its own acquire-execute-release against the plugin's underlying `sqlx` connection pool (no per-call connection pinning, no `.transaction()` helper), so a raw multi-statement transaction can span different pooled connections; this produced a real on-device `SQLITE_BUSY`/"database is locked" error (an orphaned, never-committed transaction left on one pooled connection, blocking every other connection's writes indefinitely) before being fixed. Every exported function instead runs through a module-local `enqueue()` promise queue, so this backend never has two pooled-connection calls in flight at once — the same effective serialization `webDb.ts`'s single Worker already gets for free. `getStorageInfo()` always reports `persistent: true` here — native SQLite has no in-memory-fallback case to warn about, unlike OPFS.
- `persistence.ts` — `createDebouncedSave(docId)`: coalesces rapid edits into one write after a quiet period (800ms default), rather than saving on every keystroke. Backend-agnostic — goes through `db.ts`. **Exposes a `flush()` method** (a property on the returned function, not a separate export) that immediately commits whatever's currently pending, bypassing the delay — necessary because a plain `setTimeout` keeps running regardless of the calling React component's lifecycle: without a way to force it early, leaving a document (navigating back, or the app being backgrounded) before the 800ms window elapses let the pending write race a *later* `loadDoc` call for the same doc (from reopening it) reading SQLite before the earlier write landed, silently serving stale content. Confirmed directly as a real, reproducible bug, not theoretical — see `EditorPage.tsx`'s own entry below for the exact repro and the two separate root causes involved (this flush alone did not fully fix it).
- Also intended for: custom Milkdown plugins for anything that needs document-level behavior beyond pure UI (most UI-adjacent plugins so far have stayed in `src/view/` since they're tightly coupled to the editor's own rendering, not reused app behavior).

Dependency direction is one-way: **App → Control → View → Model**. View and Model must not import from Control or App; Control must not import from App. `src/app/` is the only place that imports from both View and Control to wire them together.

## Mobile-first UI

The core design rule: **no `:hover`-dependent UI anywhere**. This replaced Crepe's hover-revealed drag handle, hover-only code-block toolbar, and mouse-driven table row/column controls, none of which have a touch equivalent.

- **Fixed bottom toolbar** (`Toolbar.tsx`) — always visible, not summoned, horizontally scrollable if it overflows rather than wrapping or hiding items behind a "more" menu. Every button is >=44px, icon-only with `aria-label`. Tapping Table/Code-block/Mermaid/HR inserts directly at the cursor — no modal, no size picker (table insert is a fixed 3×3; resizing means delete-and-reinsert, a known P0 gap, see Scope Boundaries). Active/pressed state is driven by `isMarkActive`/`isNodeActive` polling against the live selection, not `:hover`.
- **Code-block chrome** (`code-block-layout.css`) — the language picker, copy button, and preview-toggle button are all unconditionally visible and 44px-sized; there is nothing to "un-hide" since the component itself ships no CSS at all (Crepe's hover-gating was purely its own theme layer).
- **Explicitly rejected as not touch-viable**, not just "not yet styled": `@milkdown/kit/component/table-block` (row/column handles are shown via a continuous `pointermove` boundary-distance check, and row/column reordering uses native HTML5 `draggable`, both mouse-only by architecture, not CSS) and `@milkdown/plugin-block` (hover-driven drag handle). Do not reach for these later as a quick win for table/block-reorder UI — they would need to be replaced, not restyled, same as they were rejected here.

## Persistence

All persistence goes behind `src/control/db.ts`. View and App components never issue SQL directly, and never import `webDb.ts`/`tauriDb.ts` directly either — always go through `db.ts`.

**Two backends, picked at runtime by `db.ts` via `isTauri()`:**
- **Web** (`webDb.ts` + `sqlite.worker.ts`) — SQLite WASM over OPFS, in a Worker.
- **Tauri/Android** (`tauriDb.ts`) — native SQLite via `@tauri-apps/plugin-sql`, on the main thread.

**Why two backends, not one:** Android's system WebView uses one renderer process per app rather than per-origin, which is what Chrome's cross-origin-isolation mechanism (and so `SharedArrayBuffer`, and so OPFS) requires. This is a WebView platform constraint, not something fixable with COOP/COEP headers on Tauri's side. Left on the OPFS backend, the Android build would silently fall back to the non-persistent in-memory path `sqlite.worker.ts` already has a warning for (`getStorageInfo().persistent === false`, surfaced as a banner in `App.tsx`) — documents would not survive an app restart. `tauri-plugin-sql` sidesteps this entirely by going through Rust/sqlx instead of the WebView's own storage APIs.

Same two-table schema on both backends:
- **`docs`** — one row per document: `id` (uuid, generated via `crypto.randomUUID()`), `title`, `author`, `tags` (JSON array), `custom_properties` (JSON array of `CustomProperty`), `created_at`, `updated_at`. This is `DocumentMeta` persisted.
- **`blocks`** — one row per top-level markdown block within a doc: `(doc_id, position)` composite primary key, `content` (that block's own markdown string, from `splitMarkdownIntoBlocks`). `ON DELETE CASCADE` from `docs`.

`listDocs()` (ordered by `updated_at DESC`) backs the Home page; `createDoc()` makes a new empty-metadata doc and returns its id; `EditorPage` calls `loadDoc(docId)`/`saveDoc(docId, meta, blocks)` for the document it's showing.

**`EditorPage.tsx`'s `handleContentChange` (the `Editor`'s `onChange` callback) schedules the debounced save SYNCHRONOUSLY, not from inside a `setMeta` functional updater.** An earlier version did `setMeta((prev) => { const next = touch(prev); saveRef.current?.(next, blocks); return next; })` — putting the actual side effect (scheduling the save) inside the updater function React only calls once it gets around to *processing* that queued state update. **Confirmed directly as a real, reproducible bug, not theoretical**: draw a stroke (or make any edit) and then immediately navigate back to the document list and reopen the same document — before this fix, the drawing was gone, because if this component unmounts before React processes that specific queued `setMeta` update, React abandons it for the unmounting component and the updater's body — including the call that would have scheduled the save — never runs at all. Fixed with `metaRef` (mirrors `meta` for synchronous reads, same pattern as `markdownRef`) so `handleContentChange` reads the current value and calls `saveRef.current?.(...)` directly and unconditionally, independent of whether/when React re-renders. **This was one of two separate root causes behind the same symptom** — see `persistence.ts`'s own `flush()` entry above for the other (a debounce window that could still lose a save if nothing ever triggers it to fire early); both were needed together, confirmed by reproducing the bug with each fix applied alone and finding it still failed. `EditorPage.tsx` also calls `saveRef.current?.flush()` from its own unmount cleanup (covers in-app back-navigation) and from `visibilitychange`/`pagehide` listeners (covers the app being backgrounded or the tab/window closing, neither of which unmounts this component the way navigating back does).

**`DocumentMeta` (title/author/tags/customProperties) is write-once, set only at creation.** `HomePage.tsx`'s `NewDocumentModal` collects title/author/tags, then composes two already-existing calls — `createDoc()` followed immediately by `loadDoc()` + `saveDoc(docId, meta, [])` with those fields merged in — rather than `createDoc()` taking the fields itself; this keeps both backends (`webDb.ts`/`tauriDb.ts`) untouched. There is **no metadata-editing UI anywhere after creation** (this replaced an earlier always-present, collapsible `DocumentHeader` component in `src/view/`, deliberately removed): `EditorPage.tsx` shows the title read-only next to its back button and that's it. `customProperties` has no UI at all anymore — the modal only captures title/author/tags — so it's effectively unused going forward unless a future feature adds a way to set it. Content edits still call `touch(meta)` to refresh `updatedAt` for Home's sort order; only `updatedAt` changes post-creation, nothing else in `DocumentMeta` does. Revisit if write-once turns out to be too restrictive — e.g. a typo'd title currently can't be fixed at all.

On save: `saveDoc(docId, meta, blocks)` upserts the `docs` row, then deletes and reinserts all `blocks` rows for that doc inside one transaction — simplest correct approach for a single-user local editor; do not optimize this into incremental block diffing unless it becomes a measured problem.

Do not pre-build support for sync, multi-user, or versioning until a feature requires it.

**Known open question, deliberately not acted on:** the per-block `blocks` table isn't earning its keep today — every save deletes and reinserts *all* blocks (no incremental diffing), and every load immediately joins them back into one markdown string via `joinBlocksIntoMarkdown`, so right now it's equivalent to (but more complex than) a single `content` markdown column on `docs`. It's kept as-is, anticipating future block-level granularity (incremental saves, per-block history) that isn't built yet — revisit collapsing it to one column if that future need doesn't materialize, or keep it once something actually uses block-level access.

## Tauri / Android

`src-tauri/` wraps the Vite web build as a native Android app (`tauri.conf.json`: `frontendDist: ../dist`, `devUrl: http://localhost:5173`). The Rust side registers one plugin beyond Tauri's defaults: `tauri-plugin-sql` (`src-tauri/src/lib.rs`), with its commands scoped down to exactly what's used — `sql:allow-load`, `sql:allow-select`, `sql:allow-execute`, `sql:allow-close` (`src-tauri/capabilities/default.json`; Tauri 2's capability system denies plugin commands by default until granted here). `src-tauri/gen/android/` is the generated Gradle/Android Studio project (from `npx tauri android init`), not hand-maintained. **This is stronger than it sounds: regeneration isn't limited to `tauri android init`** — confirmed directly while investigating whether Android's native text-selection toolbar could be suppressed (see the View section's removed-floating-toolbar entry above) that a plain `tauri android dev`/`android build` invocation also overwrites files under `generated/` back to their template content, specifically via `rustBuildArm64Debug`'s Gradle task invoking Tauri's own `android android-studio-script` subcommand **mid-build** — a point nothing in `tauri.conf.json` (`beforeDevCommand`/`beforeBuildCommand` included) can hook into, verified by wiring an auto-reapply script into `beforeDevCommand` and observing the compiled APK still lacked a hand-patch made to `RustWebView.kt` afterward. That file is also not even Tauri's own template — it's `wry`'s (`wry-0.57.0/src/android/kotlin/RustWebView.kt`, the underlying webview crate), and neither Tauri's plugin system nor wry's own `on_webview_created` hook provide a way to supply a custom `WebView` subclass — both only receive the already-constructed instance, the same timing `MainActivity.kt`'s `onWebViewCreate` already has. **Net conclusion: no durable way exists to customize `RustWebView`'s behavior (e.g. overriding `startActionMode` to suppress the native selection toolbar) without vendoring/patching `wry` itself** — a forked core dependency to maintain across upgrades, clearly disproportionate for this project. `MainActivity.kt` (outside `generated/`) remains the one legitimate, durable customization point, limited to what `onWebViewCreate`/the `WryActivity`/`TauriActivity` base classes expose (e.g. the existing keyboard-inset listener) — anything requiring an earlier hook than "already-constructed instance" is out of reach short of that fork.

**A real, user-reported bug: `DrawLayer`'s ink strokes visibly stretch after rotating the device, and never self-correct.** Root-caused to `AndroidManifest.xml`'s `android:configChanges` (which already includes `orientation|screenSize`, needed so the Activity — and the whole React app's in-memory state — survives a rotation instead of being torn down and recreated) having no corresponding `onConfigurationChanged` handling in `MainActivity.kt` to go with it: declaring `configChanges` tells Android NOT to automatically do whatever it would otherwise do on that kind of change, which for a `WebView`-hosting Activity apparently includes not reliably re-measuring the WebView's own View against the Activity's new post-rotation window bounds (confirmed as a known, documented class of Android WebView issue when `configChanges` is used without an explicit relayout trigger — e.g. the same root cause behind `apache/cordova-android#799`). The page's own CSS layout (text, buttons, flex layout) still resizes correctly regardless, since that's ordinary browser reflow once the WebView's content area DOES get the right dimensions painted into it — but DrawLayer.tsx's canvas resize path depends on its own `ResizeObserver` firing, which depends on an actual Android layout pass happening for that element, which this app was never explicitly requesting after a config-change callback. The visible symptom matches exactly: a `<canvas>` element's OWN backing-buffer resolution (its `width`/`height` attributes, set in JS from `getBoundingClientRect()`) stays frozen at its pre-rotation size while the browser still stretches that bitmap to fill the post-rotation CSS box — the same artifact as resizing an `<img>` without updating its intrinsic dimensions. **Not reproducible via a desktop browser's instant `page.setViewport()` resize** (confirmed directly — tried non-reflowing content, content that genuinely reflows at the new width, and the virtualized/chunked path, all showed pixel-identical stroke positions before/after), since that test path never goes through this native Android codepath at all; only reproducible on a real device, where it was confirmed to be persistent (not a transient one-frame flicker that self-corrects). Fixed by storing the `WebView` reference in `MainActivity.kt` (`onWebViewCreate`, same timing the existing keyboard-inset listener already uses) and calling `webViewRef?.requestLayout()` from a new `onConfigurationChanged` override (chaining `super.onConfigurationChanged()` first, which still reaches `TauriActivity`'s own override and its `PluginManager.onConfigurationChanged()` forwarding, unaffected) — forces Android to re-measure the WebView against the Activity's already-updated window bounds, which in turn lets the page's `ResizeObserver` fire with correct final dimensions. **Not yet verified on a real device** (the fix is applied and documented here on the strength of the root-cause diagnosis and the matching known-issue precedent, not an on-device confirmation — an on-device build/deploy/rotate verification loop was attempted but abandoned as too slow/unreliable in this environment; confirm with a real device before considering this fully closed).

Run with `npx tauri android dev --host <LAN IP>` (hot-reload against the Vite dev server, needs a device connected via USB with Developer Options/USB debugging on) or `npx tauri android build`. **Pass `--host` explicitly, pinned to this machine's real LAN-facing IP** — without it, the CLI auto-picks a "public network address" to advertise to the device, and on a machine with a VPN/proxy client running (confirmed directly: a Clash.Meta/Mihomo-style "Meta Tunnel" virtual adapter using the `198.18.0.0/15` block), it can pick that virtual adapter's address instead of the real LAN interface, which the device can't route to at all (`ERR_CONNECTION_REFUSED`, even though ICMP ping to the real LAN IP succeeds — the auto-pick silently chooses the wrong interface, it's not a firewall/network-reachability problem). Also note: `--no-watch` makes the whole command (including its spawned `beforeDevCommand`/Vite dev server) exit once the initial deploy finishes rather than staying resident — fine for a one-shot build+install, but the app then has no backing dev server for any later app restart/reconnect; omit it to keep the tunnel alive for an ongoing session. Android-only: no iOS configuration exists or is planned without a Mac/Xcode.

## Scope Boundaries

**Trade-offs/risks:**
- The virtualized editor path (`VirtualizedEditorBody`, see the View section) gives each chunk its own independent Milkdown instance and undo history — no cross-chunk undo, no cross-chunk text selection, no cross-chunk drag, same limitations the vendored `milkdown-chunk-editor` package documents for itself. Accepted only because it's gated behind `CHUNK_SIZE_THRESHOLD` (50,000 chars): most documents never reach it and keep the single-instance path's full cross-document undo/selection. The threshold itself is an untuned, O(1) char-count proxy for node count (real parsing would be needed for an exact count) — revisit if it's ever measured to be wrong for real documents.
- Real-device measurement (a real Android tablet, not just headless Chrome) found a scroll-triggered chunk swap took ~14.5s before `sync()`'s recycle step existed — dominated by destroying and recreating each chunk's full Milkdown/CodeMirror/Mermaid/KaTeX stack, not by parsing markdown. Headless Chrome never surfaced this; it's fast enough there to mask the cost real mobile hardware pays for repeated `Editor.make()...create()` calls. Recycling (see the View section's `virtualizedEditorController.ts`/`chunkMount.ts` entry) fixes the common case, but the fallback create/destroy path (pool growing/shrinking) still pays the original per-instance cost — not re-measured on-device after the recycling fix (blocked by an unrelated network/firewall issue on the dev machine, see below), so its real-hardware number is unconfirmed, only expected-by-construction to match the already-measured create and destroy costs.
- `splitIntoChunks`' heading-based splitter is regex/line-based (with its own code-fence state machine), independent of and different in granularity from this app's remark-AST-based `splitMarkdownIntoBlocks` used for the `blocks` table — deliberately: chunking is a view-only concern layered on top of unchanged persistence (see the View section), not a replacement for it. A chunk boundary and a persisted-block boundary will generally land at different points in the same document; this is expected, not a bug. **Chunk size is governed entirely by heading placement, not a target size** — a document with sparse or no headings (or headings only below `splitLevel`) would produce one giant chunk, or the whole document as a single chunk, getting little or no virtualization benefit despite being large enough to trigger it. Confirmed with the user that this app's real documents mostly have headings, so this is a theoretical gap, not a measured problem — deliberately not mitigated (e.g. via a secondary size-cap that force-splits an oversized chunk at a paragraph boundary). Revisit only if a real document without adequate headings actually causes a problem; a full Word-style dynamic/reflow-based pagination (splitting by measured rendered height rather than heading structure) was considered and rejected outright regardless — it would require abandoning the stable-chunk-boundary invariant the whole recycling/`VirtualLayout` architecture depends on (a resize would become a cascading re-flow across all subsequent chunks instead of updating one array entry), and would need splitting individual nodes (paragraphs, tables) across separate ProseMirror instances, which ProseMirror has no native support for.
- `vendor/milkdown-chunk-editor-0.1.0.tgz` is a vendored tarball copy (not pulled from a registry) — upgrading it means dropping a newer `.tgz` into `vendor/` and re-running `npm install`, not `npm update`. **A plain `npm install` is not actually sufficient on its own if the version string stays the same (as it did for the 2026-10-27 upgrade)** — confirmed directly, not assumed: npm silently reused its own cached content for this `file:` dependency and reported "up to date" despite the tarball's content having changed, and even after `rm -rf node_modules/milkdown-chunk-editor` + `npm cache clean --force`, the install then failed with `EINTEGRITY` because `package-lock.json`'s pinned hash for this package was still the old one. The reliable procedure: drop the new `.tgz` into `vendor/`, delete the `"node_modules/milkdown-chunk-editor"` block from `package-lock.json` entirely (don't just edit its `integrity` field — other pinned metadata, e.g. its `peerDependencies` range, can also have changed), then `npm install` to let it re-resolve and regenerate that block fresh. `vendor/milkdown-chunk-editor-src/` is a reference-only copy of that package's own TypeScript source (`chunked-editor.ts`/`mount-chunk.ts`/`split.ts`/`virtual-layout.ts`/`style.css`, the files `VirtualizedEditorController`/`chunkMount.ts` were ported/adapted from, plus `editor-pool.ts`/`doc-cache.ts`/`index.ts` added as of the 2026-10-27 sync, new upstream files this app doesn't use) — outside `tsconfig.app.json`'s `"include": ["src"]`, so it's never compiled or bundled; kept purely as a reference, synced from the author's own separate `WorkBuddy` session/repo (`C:\Users\LaxLiu\WorkBuddy\2026-10-22-14-45-42\repo`, a real git checkout with commit history — still active as of the 2026-10-27 upgrade, not a one-time now-cleaned-up export). **The 2026-10-27 upgrade replaced `VirtualLayout`'s internal height table with a Fenwick tree** (array prefix-sum before, O(n) per `updateHeight` call; Fenwick tree now, O(log n), with a dirty-flag-gated lazy rebuild of a `top` array so `getBox(id).top` stays O(1) for reads) — verified directly against the new source that every public method this app actually calls (`setItems`/`getRange`/`getBox`/`updateHeight`/`getTotalHeight`/`scrollTargetFor`) kept an identical signature and return shape, so this was a drop-in swap; the full existing virtualized-editor CDP regression suite (13 tests) was rerun against it afterward and all still pass. The same upgrade's other changes (an `EditorPool` instance-reuse feature, `mount-chunk.ts`/`chunked-editor.ts` changes, a scroll-compensation bug fix) all live in the package's own `ChunkedEditor`/`mountChunk`, which this app has never used directly (see above) — confirmed via the upstream diff that `splitIntoChunks`/`joinChunks`/`estimateHeight`/`Chunk`/`ChunkStore` were untouched, so none of that is relevant here.
- SQLite WASM persistence is browser-local; no cross-device sync is included.
- iOS is not attempted at all (needs a Mac/Xcode) — Android is the only native target.
- `tauriDb.ts`'s SQL text is verified against a real SQLite engine in Node (same approach as the web backend). The actual JS↔Rust IPC bridge *has* now been exercised on a real device, and it surfaced a real bug: a hand-rolled `BEGIN`/`COMMIT` transaction in `saveDoc` produced an on-device `SQLITE_BUSY`/"database is locked" error, traced to `tauri-plugin-sql`'s connection-pooled `execute()`/`select()` (confirmed against its Rust source — no per-call connection pinning, no `.transaction()` helper) letting a `BEGIN` get orphaned on one pooled connection. Fixed by dropping multi-statement transactions entirely and serializing all calls through a local `enqueue()` queue instead (see `tauriDb.ts`). Residual risk: without real transactions, `saveDoc`'s docs-upsert + blocks-delete-and-reinsert is no longer atomic — a crash between those statements could leave stale blocks for a doc. Accepted for the same reason the web backend already accepts non-incremental block diffing: simplest correct-enough approach for a single-user local editor (see "Persistence" above); revisit only if it becomes a measured problem, and only via a custom Rust-side command (the JS plugin API has no way to pin a transaction to one connection).
- **Table row/column insert/delete, cell merge/split have a UI** (`tableCommands.ts`, a "Table" group in `Toolbar.tsx`) — resize still doesn't (no touch-viable way to drag a column border; still means delete-and-reinsert for resizing). Button-based, non-pointer-tracked, per the plan this gap always had. Three things worth knowing if touched again:
  - **Cell merge/split has no action-sheet/picker.** "Combine Row"/"Combine Column" merge the focused cell directly with its immediate right/below neighbor (`combineWithNeighbor` in `tableCommands.ts`) rather than requiring a drag-selected cell range — `mergeCells` (`@milkdown/kit/prose/tables`) only acts on an existing multi-cell `CellSelection`, which normally comes from a mouse/touch drag across cell boundaries, the same gesture `table-block`/`plugin-block` were already rejected for; this constructs a 2-cell `CellSelection` programmatically instead (current cell + its `TableMap.nextCell()` neighbor) and merges that, disabled at a table edge where no such neighbor exists.
  - **`toggleHeaderRow`/`toggleHeaderColumn` are not wired up, and can't be with this schema.** Verified directly against `@milkdown/preset-gfm`'s actual table schema: it uses separate node types for header vs. body (`table_header_row`/`table_header` vs. `table_row`/`table_cell`), with `table_row`'s content model only ever allowing `table_cell` children — `toggleHeaderRow`'s generic per-cell-attribute toggle (built for schemas where headerness is a cell attribute within one uniform row type) produced a real `TransformError: Invalid content for node table_header_row` against this schema, not a cosmetic failure. `toggleHeaderColumn` is worse than incompatible: GFM/CommonMark markdown has no syntax for a header column at all (only the single header row the `---|---|` separator line produces), so one couldn't round-trip through this app's markdown persistence even if the schema allowed representing it.
  - **Row operations needed hand-written guards the generic commands don't have; column operations didn't.** The same GFM schema makes `content: "table_header_row table_row+"` on the table node — exactly one mandatory header row, always first, and at least one mandatory body row. `addRowBefore` always inserts a generic `table_row`-typed node regardless of position (verified in `prosemirror-tables`' own `addRow()`, via `tableNodeTypes(schema).row` unconditionally) and `deleteRow` has no concept of "this row can never be removed" or "don't remove the last body row" — confirmed directly, not assumed: deleting the header row left an empty-but-still-present `<tr data-is-header>` plus a corrupted extra row after ProseMirror's own schema-validity repair ran. `tableCommands.ts`'s `insertRowAbove`/`deleteRow` wrap the generic commands with a row-index/row-count check (`tableRowInfo`) to disable both at row 0, and disable delete when only one body row remains. Column operations needed no equivalent guard: `addColumn` picks each row's new cell type from that same row's own existing neighbor cell (verified directly in its source), so it already produces `table_header` cells in the header row and `table_cell` elsewhere without help.
- No drag-and-drop block reordering (no touch-viable replacement for `plugin-block` designed).
- **A pre-existing, unrelated bug in the virtualized path's click-past-end handling**: `test-virtualized-codeblock-exit.mjs` fails on a document that ends in a code block, after reopening the doc and scrolling to the bottom — tapping below the code block doesn't focus the editor the way it should. Found incidentally while re-running the regression suite during the doc-JSON-cache/dirty-plugin verification above; confirmed via bisection (reverting `chunkMount.ts` to its exact pre-cache/pre-dirty-plugin state and re-running) that this fails identically against the unmodified prior code, so it's not a regression from that work. Not investigated or fixed — out of scope for that change; revisit as its own fix.
- Verified: the actual SQL schema/queries/transactions against a real SQLite engine in Node (`@sqlite.org/sqlite-wasm` explicitly supports in-memory DBs outside a browser); the markdown block-split/join round-trip against `remark`; the full `@milkdown/kit` composition (schema assembly, mark/node names, `toggleMark`/`setBlockType`/`createTable`) type-checks and builds cleanly, and every schema/API claim here was checked directly against installed package source rather than assumed. NOT verified: actual rendering/interaction in a real browser (toolbar taps, floating toolbar positioning, code-block chrome, OPFS persistence end-to-end) — unavailable in this environment. Confirm with a real device/browser session before considering this done.
- Link insertion uses `window.prompt`, not a custom UI.
- Locally-picked images are inlined as base64 `data:` URLs directly in the markdown/`blocks` content (see `commands.ts`'s `insertImage`) — there's no file storage/hosting layer, so this is the only way to keep a local image in the document at all. Trade-off: base64 inflates a block's stored size by ~33% over the raw image bytes, with no compression/resizing step, so a document with several large photos can bloat noticeably in the `blocks` table. Revisit only if this becomes a measured problem (e.g. a client-side downscale-before-encode step).

- `DrawLayer.tsx`'s annotations are now reflow-anchored AND persisted (real ProseMirror positions, remapped via `tr.mapping` on every edit, written to/read from a custom `ink` node — see the View section's `inkPersistence.ts` entry above) on **both** the single-instance and the virtualized editor paths — the virtualized path anchors each point to a specific chunk id + a local position within that chunk's own document, re-resolved against whichever live instance currently represents that chunk (`getChunkEditor`), rather than one shared position space; see `DrawLayer.tsx`'s own entry above for the three-anchoring-strategy design and `inkPersistence.ts`'s entry for the per-chunk persisted format and the bugs found building it. **Known limitation of the persisted format, both paths**: it assumes the saved markdown is never hand-edited outside this app in a way that reorders content or touches a trailing `<ink data="...">` line directly — doing so would desync anchors (wrong position numbers after re-parse) or corrupt/strip the block entirely, neither of which is detected or repaired. **Known limitation specific to the virtualized path**: a stroke's points are anchored per-chunk at the moment they're drawn, so a stroke that visually crosses a chunk boundary (rare, since chunk boundaries fall at heading lines, but possible with a short chunk or a stroke drawn across a scroll-triggered boundary) ends up with some points persisted under one chunk's `ink` node and the rest under its neighbor's — each remains individually well-anchored and persists correctly, but the stroke as a whole can show a visible seam/gap at the boundary after a reload if the two chunks' own scroll positions don't line up pixel-for-pixel the way they did at draw time. Not fixed — the chunk-crossing case is uncommon and each half still behaves correctly on its own terms; revisit only if this proves to matter in practice for real documents.

Either way, switching the document-creation step from `page.keyboard.type(...)` to a synthetic-clipboard-paste (`ClipboardEvent` with a `DataTransfer`, exercised via Milkdown's own clipboard-plugin markdown parser — see `test-android-huge-doc.mjs`'s original precedent) avoids a multi-second typing cost once documents reach tens of thousands of characters. Revisit by sizing up the rest of the suite the same way before relying on it, rather than rediscovering this script-by-script.
