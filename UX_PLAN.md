## 1. Proposed phasing

Ordered so later phases don't get blocked by earlier ones; each phase assumes prior phases are built first.

### Phase 1 — Small, additive, non-conflicting (no architecture decision needed) — IMPLEMENTED
Safe to build regardless of how items 1–10 resolve. Built and verified end-to-end via CDP (`test-phase1-ux-plan.mjs`, `debug-latex-eq.mjs`) — zero page errors, all 12 checks pass.
- **Code block "Wrap" toggle**: a real per-block button (as the design shows) isn't buildable — `@milkdown/components`' code-block NodeView ships a fixed Vue template with no slot/config hook for a custom button (confirmed directly against its source). Built instead as one document-wide toggle in the Toolbar's "Code" row (`codeBlockWrap.ts`): a shared CodeMirror `Compartment`, applied to every currently-mounted code block's own raw CodeMirror view via `EditorView.findFromDOM` (CM6's own public API). A code block created *after* the toggle is flipped starts unwrapped until the toggle is pressed again — a known, minor, documented gap (no hook exists for "a code block NodeView just mounted").
- **LaTeX auto equation numbering** (`latexPreview.ts`): pure CSS counters (`counter-reset`/`counter-increment`/`content: counter(...)`), not computed in JS — the code-block component's `renderPreview` callback has no access to its own node's position (confirmed against its source), so there's no reliable way to number blocks by document order from inside it. CSS counters number in DOM order automatically, correct regardless of insertion/deletion/reordering. Scoped per `.milkdown` root, so each virtualized chunk numbers its own equations independently (a known limitation, consistent with this app's other cross-chunk gaps). Verified visually via screenshot (`debug-latex-eq.mjs`) — `getComputedStyle(el, "::after").content` doesn't resolve `counter()`, so that check only confirms presence, not the rendered number.
- **Table: Sort column, per-column align, cell/fill color, header-column toggle, button-based row/column reorder** (`tableCommands.ts` + new `tableCosmetics.ts`): `setCellAttr`/`moveTableRow`/`moveTableColumn` (all real `prosemirror-tables` exports, re-exported through `@milkdown/kit/prose/tables`) do the real work for align/reorder — `moveTableRow`/`moveTableColumn` swap CELL CONTENT between row/column slots while each slot keeps its own existing node type (verified directly against `prosemirror-tables`' source), so moving the mandatory header row wouldn't corrupt the schema, but WOULD silently reassign header styling to whatever content got swapped in — guarded out the same way `insertRowAbove`/`deleteRow` already guard row 0 (row reorder only applies among body rows; no such guard needed for columns). Sort is a hand-rolled rebuild of the table's body-row array (sorted by a column's text content), since no generic command covers it. Header-column and cell/fill color have no GFM/markdown syntax to round-trip through at all (same hard limitation already documented for header-column) — both are client-side-only cosmetic state (`tableCosmetics.ts`, a position-keyed ProseMirror plugin remapped via `tr.mapping` on every transaction, same technique DrawLayer's own PM-anchored ink points use, rendered via decorations), lost on reload. Resize remains unsupported (delete-and-reinsert is still the only way).
- **`commands.ts`: Outdent/Indent** — thin wrappers over `prosemirror-schema-list`'s `liftListItem`/`sinkListItem`, same `list_item` type regardless of bullet/ordered list.
- **Toolbar: "Hide keyboard" button already existed** (pinned outside the scrollable row) — no new work needed there. The "pinned-vs-scrolling split" in `KeyboardPortrait.dc.html`'s own caption ("Undo + Hide keyboard stay pinned") was a small refinement: Undo moved out of the scrollable default row to sit pinned next to Hide-keyboard; Redo stays in the scrollable row.

### Phase 2 — Slash-command insert menu, web/desktop only (decision 3 resolved) — IMPLEMENTED
Built and verified end-to-end via CDP (`test-phase2-slash-blocks.mjs`) — filter/insert/arrow-nav/Escape-dismiss, callout + toggle-list insert, and a full markdown round-trip (export → paste-reparse) including the nested case (a toggle list inside a callout), zero page errors.
- `SlashMenu.tsx`: built on `@milkdown/plugin-slash`'s `SlashProvider` (added as an explicit dependency, `@milkdown/plugin-slash`) for floating-ui positioning, with a custom `shouldShow`/query-extraction (the library's own default only checks "last character is `/`", which would close the menu the instant a filter character is typed) and a capture-phase keydown listener for Arrow/Enter/Escape (same "intercept before ProseMirror's own handling" technique `codeBlockLongPress.ts`/`DrawLayer.tsx` already use). Gated behind `Editor.tsx`'s `SLASH_MENU_AVAILABLE = !isTauri()` — Tauri/Android keeps `Toolbar.tsx`'s existing tap-to-open Insert group as the only insert path, unaffected.
- **Escape-dismiss needed a real `useState`, not a ref**: Escape dispatches no ProseMirror transaction, so nothing else triggers a re-render to pick up a ref mutation — confirmed directly as a real bug (the menu stayed in the DOM after Escape with a ref-only first attempt) before switching to state.
- Wired 8 existing block types (Table, Code block, LaTeX block — a new `insertLatexBlock` helper mirroring `insertMermaidBlock`'s pattern, Mermaid, Image, Heading 1/2/3, Blockquote, Divider) plus the two new ones below. Each also got a Toolbar Insert-group entry (Callout, Toggle list, LaTeX block) so Tauri/Android users can still insert them — necessary since the underlying node types must render correctly on *both* platforms regardless of which insert path created them (a document edited on web and opened on Tauri must not show broken/inert content).
- **Callout** (`callout.ts`): reuses GitHub's own "alert" convention (`> [!NOTE]` as a blockquote's first line) rather than inventing a raw-HTML round-trip — not a remark-gfm built-in (confirmed directly: GitHub's rendering of this is its own post-processing layer, not part of the CommonMark/GFM spec remark-gfm implements), but a real, recognizable convention that degrades gracefully to a plain blockquote elsewhere. A tree-transform reclassifies the mdast node's own `.type` from "blockquote" to "callout" *before* any schema-level parsing runs, which is what lets this schema and the commonmark preset's own unconditional blockquote schema both apply correctly without either needing to know about the other. Only one callout type ships (always "note") — no type-switcher UI built, not asked for.
- **Toggle list** (`toggleList.ts`): `<details>`/`<summary>` — real, standard CommonMark HTML, collapse/expand handled entirely by the browser's native element, no custom JS for that part. Two child node types (`toggle_summary`/`toggle_body`) rather than one node with a plain string attr, the same structural pattern the GFM table schema itself uses for its header/body row split — gives real, directly-editable ProseMirror content for both the title and body with no NodeView/contentEditable-wrangling needed for the title. `toggle_summary` is plain-text-only (no marks) since markdown inside the opaque `<summary>` tag text is never interpreted as markdown by remark at all — allowing marks there would silently fail to round-trip them. A `collapsed` attr (live-editing-state only, not persisted — same tradeoff as `tableCosmetics.ts`'s header-column) plus a small custom NodeView keeps a user's native open/close click in sync with it; newly-inserted toggle lists default to open so typing can start immediately. **A real, non-obvious bug found and fixed during this work**: `@milkdown/preset-commonmark` ships its own remark plugin that normalizes *every* top-level HTML node into a paragraph wrapping a single HTML child, regardless of registration order relative to this plugin (confirmed directly against its source) — the exact same finding `inkPersistence.ts`'s own `convertInkNodes` already documents for its `<ink>` tag. The open/close-marker merge had to check for this paragraph-wrapped shape too, or it silently never matched at all (confirmed directly: a pasted toggle list rendered as Milkdown's generic inert HTML-passthrough node, not as a real toggle, until fixed).
- **Inline math deferred to Phase 7** (a re-sequencing from the original plan, not a scope cut): unlike Callout/Toggle-list, there's no existing real-world markdown convention remark-parse already tokenizes distinctly for `$...$` inline math — building it now would mean either a new dependency (`remark-math`) or a hand-rolled regex-based text-splitting transform with real ambiguity risk (bare `$` signs in ordinary prose, e.g. "$5 or $10"). UX_PLAN.md's own Phase 7 entry already anticipated inline math pairing naturally with the dedicated LaTeX editor's node-type work, so this isn't a new decision, just acting on the sequencing already written down.
- Deferred, unchanged: Link to page (blocked on decision 4 — page hierarchy doesn't exist yet), "Drawing space" block (ambiguous vs. the existing whole-page `DrawLayer` overlay, not resolved).

### Phase 3 — Page hierarchy (decision 4 resolved: build it) — IMPLEMENTED (core scope)
Built and verified end-to-end via CDP (`test-phase3-hierarchy.mjs`) — 3-level nested tree creation, breadcrumb rendering, breadcrumb-click navigation, and delete-reparents-children, zero page errors.
- **Schema**: a nullable `parent_id TEXT REFERENCES docs(id) ON DELETE SET NULL` column on `docs`, added to both backends' `CREATE TABLE` (fresh databases) *and* via a runtime migration (`PRAGMA table_info(docs)` existence check, then `ALTER TABLE ... ADD COLUMN`) for databases that already existed before this change — this app's first-ever schema change, and real on-disk data already existed from earlier testing this session, so a bare `CREATE TABLE IF NOT EXISTS` alone wouldn't have reached it. Verified directly against a real SQLite engine (not assumed) that the ALTER statement is valid and that FK constraints on a backfilled column aren't retroactively checked against existing rows.
- **`ON DELETE SET NULL` (re-parent to root), not CASCADE**: deleting a parent silently cascading to delete all its descendants would be a surprising amplification of "delete this one document" that Home's own existing confirm-prompt doesn't warn about (it would need to say how many descendants, which the current single-doc-only confirm flow doesn't support) — re-parenting children to the top level avoids data loss outright, matching this app's existing safety-conscious bent elsewhere.
- **`createDoc(parentId)`** threaded through all four persistence layers (`db.ts`/`webDb.ts`/`tauriDb.ts`/`sqlite.worker.ts`); `parentId` defaults to `null` (top-level) so every existing call site keeps working unchanged. Kept as a separate parameter rather than added to `DocumentMeta` — it's a structural fact about where a doc lives in the tree, not user-editable metadata, same category as `id` itself. No reparenting UI — set once at creation, matching the existing "`DocumentMeta` is write-once" precedent.
- **`HomePage.tsx`**: flat list → recursive tree view, built client-side from the existing flat `listDocs()` result (no recursive SQL query — this app's own document count is a single user's personal notes, not a shared wiki at scale). Each row gets a new "+" button to create a sub-page directly under it, reusing the existing `NewDocumentModal` with the clicked node's id passed through as the new doc's `parentId`.
- **`EditorPage.tsx` breadcrumb**: the ancestor chain is built via sequential `loadDoc` calls walking `parentId` pointers (root-first), not a dedicated bulk/recursive query — simpler given this app's own shallow-tree scale, with a cheap iteration cap against a hypothetical cycle. Each ancestor segment is a real link (a new `onOpenDoc` prop, threaded through `App.tsx` the same way `HomePage`'s already was) that navigates directly there, not just a label.
- `PortraitDrawer.dc.html`'s mobile drawer is a restatement of the same sidebar — no separate design decision, just a responsive layout variant; not built as part of this pass (no portrait-specific layout work was in scope here).
- **"Link to page" deliberately NOT built as part of this phase** — UX_PLAN's own phasing lists it under Phase 2's deferred items, unblocked now that the hierarchy exists, but it's a real separate scoping decision on its own (markdown syntax for an internal link, and critically, how to resolve it to a stable docId given titles aren't unique and there's no rename UI yet to worry about link rot from). Revisit as its own follow-up rather than bundled into this already-substantial phase.

### Phase 4 — Consolidate `ModeHeader` into the bottom `Toolbar`, auto-derived mode — IMPLEMENTED
Built and verified end-to-end via CDP across two rounds — first `test-phase4-toolbar-consolidation.mjs` with an explicit mode toggle, then rewritten after a mid-phase redesign (below) to test auto-switching instead: no manual Text/Draw buttons in the DOM, Draw mode is the default with nothing focused, a stroke draws correctly in that default state, the "Edit text" button focuses the editor and switches to Text mode, the rich toolbar row shows while typing (draw row hidden), Bold still works, hiding the keyboard auto-switches back to the draw row, Paging is reachable from both rows, and Text mode holds while a group panel is open (its own deliberate blur doesn't flip to Draw) — zero page errors. Re-ran Phases 1–3's own regression suites afterward (after fixing their own reliance on a plain content click to focus the editor, see below) with zero regressions, plus a clean `tsc --noEmit` and a clean production build.
- **This phase shipped in two passes.** The first pass (decision 1 resolved: keep the explicit mode toggle) moved `ModeHeader`'s controls into a permanent `modeRow` stacked above the rich toolbar, with `DrawLayer`'s hit-testing/`pointer-events`/view-blur-on-draw wiring untouched. Verified and documented as IMPLEMENTED. A follow-up request then reopened decision 1 itself: **no manual mode-toggle button at all** — mode should be derived from whether the user is actually using a text-editing function, defaulting to Draw otherwise — **and** the toolbar should be a single row (the stacked mode-row-plus-rich-row layout didn't match the design). This second pass is what's described below and is what's actually in the codebase now; the first pass's `modeRow` is gone.
- `ModeHeader.tsx`/`mode-header.css` stayed deleted from the first pass — nothing needed to stay pinned above content once its controls had a new home. `EditorMode`/`DrawAnchorMode`/`PenStyle`/`PEN_STYLES` live in `drawTypes.ts` (moved there in the first pass, unchanged since), since `DrawLayer.tsx`/`freehandStroke.ts` both still need those types/values and neither should import from the Toolbar.
- **Mode derivation** (`Toolbar.tsx`'s `effectiveMode`): `"text"` whenever the editor has real DOM focus, a group panel is open, or a media/code-block node is selected (`textEditingActive`); `"draw"` once that stops being true. **Deliberately not keyed off `keyboardInset`** (confirmed directly against `useKeyboardInset.ts`'s own source before relying on anything here): that hook tracks an on-screen keyboard's actual height for layout/positioning only, and stays `0` on desktop or with a hardware keyboard even while the editor is genuinely focused and being typed into — using it as the mode signal would have silently made Text mode unreachable on any device without an on-screen keyboard. A new `useViewFocused(view)` hook (a `focusin`/`focusout` listener on `view.dom`, same technique `useToolbarSuppressed` already used for a narrower purpose) tracks real focus instead. `drawDisabled` (still passed from `Editor.tsx`, `isVirtualized ? !anyChunkMounted : !editor`) clamps `effectiveMode` to `"text"` during either path's own startup window, for the same reason it always has (DrawLayer can't anchor a stroke before an editor/chunk exists).
- **A second, user-reported correction landed right after the first verification pass**: the first version computed `effectiveMode` as a pure function of `textEditingActive` recomputed fresh every render (`textEditingActive ? "text" : "draw"`), which made a fresh, never-touched document default to Draw mode on load — nothing has been focused yet, which that pure computation can't distinguish from "the user just finished editing." Reported directly ("it should be Text mode") and fixed by turning the derivation into a small falling-edge state machine instead of a pure function: `derivedMode` starts at `"text"` and only changes to `"draw"` when `textEditingActive` transitions from `true` to `false` (tracked via `wasTextEditingActiveRef`, compared each run inside the same `useEffect`) — idle-with-nothing-ever-focused stays `"text"` (the falling edge never fired), while deliberately dismissing the keyboard, closing a group without reselecting, or deselecting a node all correctly still fall to Draw, since those really are true→false transitions. Verified end-to-end via CDP: fresh load shows the rich text row (not the draw row); tapping content directly now focuses the editor immediately (no longer blocked by the canvas, since Text is the default and the canvas is inactive until Draw is actually entered); typing lands correctly; dismissing the keyboard falls to Draw mode; drawing works there; "Edit text" returns to Text mode; Bold and Paging (both rows) still work; a group panel still holds Text mode throughout. The existing CDP test helpers across Phases 1/2 (`focusEditor`) were simplified to match: click directly on `.ProseMirror` when already in Text mode (the common case now), falling back to the "Edit text" button only if Draw mode happens to already be active.
- **One row, not two**: the toolbar's single child is now a ternary on `effectiveMode` — `drawModeRow` (pen-style swatches, Pin/Sketch, Paging, "Edit text") while in Draw mode, or the existing rich content (group panel / media-selection bar / default format row) while in Text mode — never both stacked, matching the design. Paging is duplicated as a pinned icon in both rows (next to Undo/Hide-keyboard in the text row) rather than living in a shared top strip, since decision 10's "relevant in both modes" reasoning still holds but there's no longer a strip both rows share.
- **A real, serious UX problem was found and explicitly confirmed with the user before finalizing this**: with Draw as the auto-selected default, `DrawLayer`'s canvas (unchanged, pre-existing architecture: `pointer-events: auto` while `active`) covers the content area and intercepts a plain tap intended to place the text cursor — confirmed directly via CDP (`document.activeElement` stayed `<body>`, typed text never reached the document). The user was presented with this concretely (not hypothetically) and confirmed the accepted trade-off: a single pinned "Edit text" button (`view.focus()`, calling through a button in the toolbar, which the canvas never covers — same reason `ModeHeader`/`Toolbar` themselves were never covered) is the one explicit way back into Text mode; tapping content directly while idle does not. Reworking `DrawLayer` to distinguish a tap-to-focus from a drag-to-draw gesture on the same content area was considered and explicitly declined as disproportionate — it would touch the gesture-routing architecture (two-finger-pan detection, long-press code-block selection, click-past-end) that decision 1's original (first-pass) resolution specifically said not to touch.
- **Existing CDP regression scripts needed a matching fix**: Phases 1 and 2's test scripts used a plain `page.click(".ProseMirror")` to establish initial focus, which the draw canvas now silently intercepts the same way a real tap would. Fixed by adding a `focusEditor(page)` helper (clicks "Edit text" if present, a no-op if already in Text mode) to `test-phase1-ux-plan.mjs`/`test-phase2-slash-blocks.mjs` in place of that initial click — mid-test re-focusing elsewhere in both scripts needed no change, since mode stays "text" continuously once genuinely entered (group-panel opens/closes keep `textEditingActive` true throughout via `activeGroupKey`, not just DOM focus). Phase 3's suite never depended on editor focus at all (tree/breadcrumb navigation only) and needed no change.
- **Visual restyle** (`toolbar.css`, unchanged from the first pass) matches the Claude Design's `KeyboardLandscape.dc.html`/`KeyboardPortrait.dc.html` accessory-bar look (chosen over `Main.dc.html`'s floating centered pill, since this app's existing full-width/horizontally-scrollable structure is a deliberate prior decision, matching the accessory-bar's shape, not the pill's): gray bar background, borderless icon buttons with a light-blue active tint, a separate white-active-state pencil-tool pill for pen-style selection (matching the design's own distinct treatment there), a blue-accent filled "Insert" button, and thin vertical separators between control clusters.

## Scope Boundaries

**Trade-offs/risks:**
- Phase 3 (page hierarchy) was a persistence schema change on two separate backends (web OPFS, Tauri native SQLite) that had to stay in sync — both got the same `parent_id` column, the same migration check, and the same `ON DELETE SET NULL` behavior, verified via CDP. The Tauri/native-SQLite side specifically (actual `tauri-plugin-sql` IPC, not just the SQL text) was not re-verified on a real device after this change — the original "verified in Node, not on-device" caveat from this app's own persistence docs still applies here too.
- Phase 4 (toolbar consolidation) and Phase 5 (floating toolbar, now web-only) are smaller in scope than originally feared — decision 2's `isTauri()` gate removes the on-device collision risk for Phase 5 entirely — but Phase 4 still touches `DrawLayer`/`Toolbar`/`ModeHeader` wiring that was arrived at after real, documented iteration this session, so it isn't purely cosmetic. Decision 1 itself was reopened and reversed mid-session (see Phase 4's own entry): there is no manual mode toggle anymore, and **tapping document content directly while in Draw mode does not focus the editor** — the draw canvas intercepts the tap first, by design, unchanged from the original architecture.
